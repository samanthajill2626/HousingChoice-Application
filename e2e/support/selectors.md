# Selector conventions

Accessibility-first, in priority order. These double as the snapshot the
Playwright MCP reads, and they pressure the UI toward accessibility.

1. **`getByRole(role, { name })`** — buttons, links, headings, textboxes.
2. **`getByLabel(text)`** — form fields associated with a `<label>` / `Field`.
3. **`getByText(text)`** — visible copy / status messages.
4. **`getByPlaceholder(text)`** — only when no label exists.
5. **`data-testid`** — last resort, ONLY when none of the above can identify an
   element. None are needed today; add one (and note it here) if a future
   element is genuinely unaddressable.

| Contact page (timeline) | a CALL card | `getByRole('region', { name: 'Communications and activity' }).getByRole('group', { name: /^Outgoing call\b/ })` - inbound is `/^Incoming call\b/`. The card's accessible name is `<direction word> - <time to SECONDS>` (e.g. `Outgoing call - 9:14:07a`; the VISIBLE clock stays at minutes, the name carries seconds so a redial inside one minute still gets its own distinct name). Seconds make a card ADDRESSABLE, NOT automatically unique to a locator: the anchored-prefix regex above is a MULTI-MATCH form that resolves to EVERY outbound card on the page, so on a thread with more than one call of that direction it is a strict-mode violation. Uniqueness of the NAME is not uniqueness of the MATCH. On such a thread either pass the FULL name (`{ name: 'Outgoing call - 9:14:07a', exact: true }`, which targets exactly one card) or narrow the prefix regex with `.first()` / `.nth(i)`. The name DELIBERATELY excludes the outcome, which flips with the live `Ringing...` / `In progress` clauses; a locator built on the outcome inherits that race. Anchor the regex - Playwright matches an accessible name by substring. Assert the outcome as the chip's own text WITHIN the located card (`toContainText`), in the direction's own vocabulary: outbound `Connected` / `No answer` / `No team answer` / `Outcome unknown`, inbound `Answered` / `Missed` / `Voicemail`, either side `Not completed` (a refused call). ALWAYS give such an assertion an API-level precondition that the terminal Dial summary landed (poll `callTimeline` for the stored `call_outcome`) - a fresh row reads `Ringing...` for 90 seconds by design. Direction ALIGNMENT is proved with real `boundingBox()` geometry, never a class name |
| Contact page (timeline) | a call card's detail reveal | `getByRole('button', { name: 'Details' })` SCOPED to the call card - it discloses the `to/from <number> - <time>` line. NOTE that this is a DEFENSIVE rule you cannot currently reach from this page: masked call rows are relay-only, and the contact timeline excludes `relay_group` conversations, so every call card on this surface today HAS a party phone and HAS the button. Do not go looking for a masked call card here to test it. Scoping is mandatory: the same page carries a `Details` card heading, and every call card WITH a party phone offers this button. | Thread (any multi-party bubble) | per-recipient delivery rows | `getByRole('list', { name: 'Delivery by recipient' })` plus named rows such as `getByRole('listitem', { name: 'Ann Tenant - Delivered - RCS' })`. REVEALED ONLY - see the row above: the list is conditionally rendered, so an absence assertion (`toHaveCount(0)`) written WITHOUT the click passes on a completely broken build. Included rows are roster members first in roster order, then keys matching no member in map order. An `excluded` slot without a suppression code is omitted; an opted-out `excluded` slot and a source-time state-absent slot remain. Each row name uses stable ASCII ` - ` separators: member identity, existing delivery text, requested/actual transport text, then optional time. This keeps duplicate rows separately addressable without replacing identity or delivery status. Transport examples are `RCS`, `RCS -> SMS`, and requested-only `MMS`. Delivery examples include `Delivered`, `Sent`, `Sending` + U+2026, `Sent - not confirmed`, `Queued - not confirmed`, `Failed`/`Undelivered` with reason/code, `Not sent - opted out (Twilio skips them)` on a group text, and `Not sent - opted out` on a relay. The app-owned `transient_cap` and `enqueue_failed` codes render as `Failed - Sending gave up after repeated carrier deferrals` and `Failed - Sending could not be scheduled` without a raw-code tail, and the four app-owned relay-retry close codes render the same way, prose with no `(error N)` tail: `retry_group_closed` -> `Not retried - group closed`, `retry_member_removed` -> `Not retried - no longer in this group`, `retry_number_changed` -> `Not retried - number changed since`, `retry_opted_out` -> `Not retried - opted out`, so a refused ladder reads e.g. `Undelivered - Not retried - number changed since` - and since retry-send-window (D3) it reads so AT ONCE when the 30003's own claim already sees the refusal, instead of `Retrying` for 1 to 4 minutes. A fifth close code, `retry_window_closed` (the retry would have gone out more than 15 minutes after the member's original leg), carries NO display code: the row keeps the original's 30003 and reads `Undelivered - Phone unreachable (error 30003)`, a plain failed attempt. Its no-tail fallback `Not retried - message too old` (`INTERNAL_CODE_REASONS`) exists only for a future surface that renders the code directly; no current surface does. A RELAY 30003 IS A LADDER, NOT A DEAD END: while a retry is CLAIMED the row reads `Retrying - Phone unreachable (error 30003)`, once a rung delivers it reads `Delivered on retry`, and only a capped, refused or window-declined ladder reads `Undelivered - <reason>`. Nothing on a relay bubble ever promises `will retry`; `Retrying` is derived from a retry row that actually exists, never from the error code. A native group text promises nothing either (no retry exists for one, retry-send-window D11): its 30003 leg reads `Undelivered - Phone unreachable (error 30003)`. `will retry` now appears ONLY on a one-to-one bubble - see the next row. The rollup chip above these rows states the same facts in its own grammar - `delivered N/M - K retrying` while claimed, `delivered N/M - K on retry` once the ladder delivered - and a delivered retry appends a SECOND bubble carrying the same body whose own chip reads `delivered 1/1 on retry`. Rows render on outbound multi-party bubbles and inbound relay-source bubbles with outbound fan-out slots, but never on 1:1 rows, a `queued_pending` hold, or an empty included map. Arm delivery outcomes with `setDeliveryOutcome` (see the Fake Twilio rows below); explicit transport fixtures own requested/actual facts. |
| Thread (one-to-one bubble) | failure chip, retry promise, Retry action | Address the bubble exactly as the meta-reveal row above does - `getByText('<body>', { exact: true }).locator('xpath=..')` - and read its chip with `toContainText`; the chip is `<delivery label> - <reason>`. A 30003 promises a retry ONLY while the failed message carries a live `retry_due_at`, i.e. an automatic retry is scheduled (retry-send-window D8): the chip reads `Undelivered - Phone unreachable - will retry (error 30003)` and the bubble offers NO Retry action. Without a live stamp (retries exhausted, a declined retry, an automated text on a manual-mode thread) it reads `Undelivered - Phone unreachable (error 30003)` and offers Retry - UNLESS the row carries `retry_outcome: 'unconfirmed'` (retry-send-adoption R5): the automatic retry's outcome was unknown and could not be resolved (the send.reconcile job closed it `unresolved`, or the retry job did after a second unknown), so it may or may not have reached the member; the promise is withdrawn and the chip reads `Undelivered - Phone unreachable - retry not confirmed (error 30003)` with NO Retry action, for good. That third reading keys on `retry_outcome`, never on the withdrawn stamp (`retry_due_at` `1970-01-01T00:00:00.000Z`) alone: RSW's enqueue-failure withdrawal writes the same stamp with no outcome and keeps offering Retry. The action is `getByRole('button', { name: 'Retry sending this message' })` (visible text: a U+21BB glyph plus `Retry`) and is NOT behind the reveal. Its ABSENCE proves something only at the same instant as the promise text: once the automatic retry lands the failed bubble is hidden (a later row whose `retry_of` names it supersedes it) and a re-resolved locator lands on the delivered retry's bubble, which has no action either - so filter ONE locator on both (`.filter({ hasText: <chip> }).filter({ hasNot: <the button> })`) and keep a positive control (a failed bubble that does show the action), as `one-to-one-30003-retry.spec.ts` does. A Retry pressed during the wait (a stale tab) is refused 409 `retry_pending` and the composer's error slot reads `A retry is already scheduled for this message.` The same slot (the text composer's `role="alert"`) carries retry-send-adoption's two refusals: 409 `superseded` (the pressed row already has a retry child) reads `A newer attempt already exists for this message.` and 409 `retry_unresolved` reads `This retry couldn't be confirmed - send a new message instead.` - but ONLY after a UI press, which on an unconfirmed row takes a stale tab (the button is hidden); a direct `page.request` press gets the JSON `{ error }` alone, as `retry-send-adoption.spec.ts` asserts. On a lane the first automatic retry goes out 10 s after the failure (`E2E_SEND_RETRY_BACKOFF_MS`, `scripts/e2e-session.mjs`); a retry whose outcome is unknown goes to the reconcile, whose three checks run 2 / 4 / 8 s after the attempt (`E2E_SEND_RECONCILE_DELAYS_MS`), so an unresolved retry reads `retry not confirmed` about 18 s after the failure. Meanwhile the promise is REFRESHED (to the attempt + 8 s + 120 s at the hand-off, then to the re-drive + 180 s), so `will retry` can outlive the 10 s backoff. |

## Narrow viewport (contact-rosters spec 6.7)
`e2e/support/viewport.ts` is the ONE definition: `NARROW_360` (the 360x800 phone
width the spec names), `WIDE_RESTORE` (1280x900 - "widen back past the 860px
twoPaneShell breakpoint", not a byte-exact restore of the 1280x720 project
default), `expectNoHorizontalOverflow(page, where)` for ROUTE content, and
`expectNoHorizontalOverflowIn(locator, where)` for ONE element's own box.

**Never hand-roll an overflow check on `document.documentElement` - in this shell
it is vacuous.** The app clamps the document to the viewport by construction
(`html, body, #root { height: 100% }`, `.shell { display: flex; height: 100% }`,
`.main { flex: 1; min-width: 0 }`) and every route renders inside
`<main class=.content>`, which is `overflow-y: auto` - and per CSS Overflow L3 a
`visible` other axis computes to `auto` once one axis is not visible/clip, so
`<main>` is an x-scroll container too. Wide route content therefore scrolls
INSIDE `<main>` and `documentElement.scrollWidth` never moves off `clientWidth`.
`expectNoHorizontalOverflow` measures BOTH boxes and asserts on the worse one;
the documentElement expression on its own can never fail.

**A `position: fixed` surface needs its OWN box measured.** The Modal backdrop is
`position: fixed; inset: 0`, and an out-of-flow box contributes to the scrollable
overflow of NEITHER the document NOR `<main>` - so the page-level helper is blind
to every dialog, whichever box it reads. Assert on the dialog itself:
`expectNoHorizontalOverflowIn(page.getByRole('dialog', { name }), where)`. It
reads that element's own scrolling area (an `overflow: visible` box still reports
its descendants' overflow in `scrollWidth`, which is how a too-wide footer shows
up), with one blind spot to size the locator against: Modal's `.body` is
`overflow: auto`, so body content self-contains - pass the innermost box you mean.

Rules every 360px block follows: assert REAL `boundingBox()` geometry, never CSS
text or computed styles; restore with `WIDE_RESTORE` before the rest of the test
continues (`playwright.config.ts` runs `workers: 1` + `fullyParallel: false`, so
a viewport left narrow mid-test poisons its own later steps); assert the 44px
touch target on the ROW container, never on a button (the glyph buttons are
~18-42px wide by design - spec 6.7 says the ROW is the target).
