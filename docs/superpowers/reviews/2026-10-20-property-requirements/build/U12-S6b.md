### Landlord page - the Requirements / Qualifications card (`LandlordRequirementsCard.tsx`)

  (`LandlordFile.tsx:164-170`).
- Title: an h3 `Requirements / Qualifications`. The shared Card puts its
  aside INSIDE the h3, so the heading's accessible name is
  `Requirements / Qualifications Apply to properties Edit requirements` when
  both actions are present. Match it with
  `/^Requirements \/ Qualifications/`, never exactly.
- Actions (buttons in the h3 aside):
  - `Apply to properties`: the visible text is the name. With no property of
    record it is `disabled`, and its accessible description is the visible
    paragraph `This landlord has no properties yet.` (aria-describedby).
  - `Edit requirements`: an aria-label; the visible text is `Edit`. It opens
    the existing landlord edit form (the page's `onEdit`).
- The only headings are the h3 title and four h4 groups: `Screening`, `Pets`,
  `Move-in costs`, `Touring`.
- One `role="group"` per item, named by the item label: `Evictions`,
  `Credit score`, `Income requirements`, `Qualifications`, `Pets`, `Deposit`,
  `Application fee`, `Touring`.
  - The value is `formatItemValue` (e.g. `No pets; pet fee $300`,
    `One month's rent; flexible`, `Self-guided; Lockbox code by text`), or

  - Multi-item groups (Screening, Move-in costs) also show the item label as

  - Group names collide with the edit dialog's fieldsets (OR-21): scope every
    group query to the card's `section`.

  - Line 1: `Updated <N> properties`, or `Updated 1 property`.
  - When any were skipped: `<M> skipped`, then one `<li>` per skipped

  - Reasons: `changed since you opened this - review it again`

### Apply to properties dialog (`ApplyRequirementsDialog.tsx`)

- `role="dialog"` named `Apply to properties`, the Modal's `wide` variant
  (56rem on a desktop, one column below 860px).
- States:
  - while reading: `Loading...`;
  - a failed landlord OR properties read: `role="alert"` with
    `Couldn't load this landlord's properties.` and a button `Try again`.
- Notices (`<p role="alert">`, above the columns, kept until the next
  Update):
  - first request 409 `requirements_changed`:
    `This landlord's requirements changed. Review the updated list and press Update again.`;
  - first request failing any other way:
    `Couldn't update the properties. Review the list and press Update again.`;
  - a later batch answering 409 or failing:
    `Updated <N> properties before this stopped. Review the rest and press Update again.`
    (`Updated 1 property before this stopped. ...` for one).
  - Each re-reads the landlord and its properties.
- Left column: a `<fieldset>`, i.e. the group `What to copy`.
  - One `<li>` per item (8), each with one checkbox named by the item label.
  - The checkbox's description is the landlord's value (`formatItemValue`),
    or `Clears` for a blank item; `Clears` is also visible text in the row.
  - Filled items start checked, blank ones unchecked (OR-17 after a stop or a
    failure: what staff chose, narrowed).
- Right column: an h3 `Which properties` labelling a `<ul>`, i.e. the list
  `Which properties`.
  - One `<li>` per property of record (not deleted), with exactly ONE
    checkbox named by `propertyRowLabel(unit)`: `<address> - <N>BR` when beds
    are known, else the address, else the unitId. Example:
    `1450 Joseph Blvd - 2BR`.
  - Then the status badge text (`Available`, `Occupied`, `Setup`, ...), then
    the changes line (the checkbox's description). It lists the checked items
    that would change, by item label, joined by `, `, in DISPLAY order
    (Screening items before Pets). Each own value is followed by
    ` (own value)`, e.g. `Credit score, Pets (own value)`. A row with no
    change reads `Already matches` and its checkbox is disabled.
  - With no property: `This landlord has no properties yet.`.
  - There is no Select all.
- Footer: buttons `Cancel` and `Update <N> properties` (`Update 1 property`).
  Update is disabled at 0 rows, while reading and while sending. Every
  control is disabled while sending; Cancel / Escape / backdrop do nothing
  then.
- Props: `{ contactId; onLandlordRead(contact); onClose(wrote: boolean);
  onDone(summary: ApplyDoneSummary) }`.
  - `onClose(true)` after any Update was sent (the page re-reads its
    properties); `onClose(false)` otherwise.
  - Every landlord read is handed to `onLandlordRead`; the page passes
    `setContact`.

### Requests the dialog sends

- Reads (on open, Try again, and after every 409 or failure):
  `GET /api/contacts/<id>` (signalled), plus `GET /api/units?limit=100&landlordId=<id>`
  walking `cursor` (signalled; fetchAllPages label `units:landlord`). The
  answer is still filtered to `landlordId === contactId` and a blank
  `deleted_at`.
- Write: `POST /api/contacts/<id>/requirements/apply`, unsignalled, in
  batches of at most 100 checked rows, one after another. Body:
  - `units: [{ unitId, ownItems }]`, the checked rows in list order.
    `ownItems` = that row's changing items that are own values, in display
    order (`[]` for none).
  - `items`: the checked items, in display order.
  - `expected`: for each listed item, every one of its unit keys as
    `landlordItemValue` reads the landlord the dialog showed, `null` for
    blank. Example: `pets: { no_pets: true, pets: null, pet_fee: '$300' }`.
- After a later batch's 409 or failure, no further batch is sent.
