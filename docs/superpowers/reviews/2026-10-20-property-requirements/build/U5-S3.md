## CONTRACT (what later units rely on)

### POST /api/contacts/:contactId/requirements/apply (`app/src/routes/contactRequirementsApply.ts`)

New module, exports `registerRequirementsApplyRoute(router, deps)` (`:136`)
and `interface RequirementsApplyDeps { contacts: ContactsRepo; units: UnitsRepo; audit: AuditRepo; logger: Logger }`.
Registered by `createContactsRouter` right after the caseworker routes
(`contacts.ts:1229-1234`), before GET `/:contactId`; same mount
(`/api/contacts`), auth and CSRF as every contacts route. The real repos
come from the contacts router's deps (`api.ts:896-927`), the harness wires
`world.contactsRepo` / `world.unitsRepo` / the audit fake by reference.

Request body: `{ items: string[], expected: { <item id>: { <unit key>: string | number | boolean | null } }, units: [{ unitId: string, ownItems: string[] }] }`.

Refusals, in this order, each writing nothing (`:145-176`):
1. 404 `{ error: 'contact_not_found' }`: no contact, or a phone / email
   pointer row. Decided on a CONSISTENT read, before the body is read.
2. 400 `{ error: 'contact is not a landlord' }`: stored `type` is not
   `landlord` (a property manager is a landlord-typed contact, so it passes).
3. 400 `{ error: <message> }` for the body, checked in this order
   (`:73-134`, strings `:41-47`):
   - `items must be a non-empty array of requirement item ids` - missing,
     not an array, empty, or any entry not one of the eight item ids. A
     repeated id is de-duplicated, not refused (AR15).
   - `expected must hold exactly the listed items, each with exactly its keys` -
     not a plain object; its item set differs from the (de-duplicated)
     listed set; an item value that is not a plain object; an item whose key
     set is not exactly that item's unit keys.
   - `expected values must be a string, a number, a boolean or null` - any
     other value (an object, an array). `false` and null read as blank;
     `true`, strings and numbers are kept and compared by D1 equality (so
     `''` is blank too).
   - `units must be a non-empty array of at most 100 properties` - missing,
     not an array, empty, or more than 100.
   - `each entry of units needs a unitId string` - an entry that is not an
     object or whose `unitId` is not a non-empty string.
   - `units must not repeat a unitId`.
   - `each entry of units needs ownItems, a list of items from items` -
     missing or not an array, or an entry that is not a listed item id
     (`[]` is valid; repeats are de-duplicated). Every entry's `unitId` and
     repeat checks run before any entry's `ownItems` check.
4. 409 `{ error: 'deposit_conflict' }`: the landlord holds
   `req_deposit_one_month: true` and a finite numeric `req_deposit`.
5. 409 `{ error: 'requirements_changed' }`: any listed item's CURRENT
   `landlordItemValue` is not `itemValuesEqual` to `expected[item]`.
   Unlisted items are never compared and never copied.

Then per unit, in request order (`:181-220`): a CONSISTENT
`units.getById(unitId, { consistentRead: true })`, the route's own
`structuredClone` of it, `planUnitApply` (S1) on the clone, then ONE
`units.applyRequirements(clone, plan.patch)` (S2) - conditioned on the unit
existing, not deleted, with this `landlordId` and the `requirement_sources`
it read. A `ConditionalCheckFailedException` skips the unit as
`changed_during_apply` and the run goes on; any other error is rethrown
(Express 5 -> 500) with no partial report (AR17) - earlier units stay
applied.

200 `{ updated: string[], skipped: Array<{ unitId: string, reason: ApplySkipReason }> }`,
both in request order. Skip reasons:
- `not_found` - no unit with that id.
- `deleted` - a non-empty `deleted_at` (a blank one is live, PR1-8).
- `landlord_changed` - the unit's `landlordId` is not this contact.
- `already_matches` - no listed item differs by INTERPRETED value (a legacy
  boolean `pets` that already reads as the landlord's value is not
  rewritten). Checked BEFORE own values, so a unit with nothing changing is
  `already_matches` whatever it holds.
- `changed_since_opened` - a CHANGING item is an own value (`set_here`, or
  never touched and non-blank) not listed in that unit's `ownItems`.
- `changed_during_apply` - the conditional write lost (a landlord or map
  change, a delete or a vanish after the read).

A written unit gets every key of each changing item set to the landlord's
value (null = REMOVE, so a blank landlord item clears it and a legacy pets
pair is rewritten whole), `requirement_sources` = its stored map with each
changing item `copied` (a listed item that already equaled the landlord
keeps its record), and `updated_at` (the repo stamps it). The landlord
contact is never written. Audit per written unit (`:210-219`):
`units#<unitId>` / `unit_updated` / `{ actor, fields: plan.changedKeys, reason: 'requirements_applied', landlordId: <contactId> }` -
`fields` = the unit keys whose STORED value changed, never
`requirement_sources`. Best-effort (AR16): a failed append logs warn
`requirements apply: audit append failed (best-effort)` with
`{ err, contactId, unitId }` and the unit stays in `updated`. Other logs
(ids and counts only): info `requirements apply refused: deposit_conflict`
`{ contactId }`; info `requirements apply refused: requirements_changed`
`{ contactId, item }`; info `requirements applied via api`
`{ contactId, items, updated, skipped, actor }`. No SSE event.
