## FLAG

### R1-12 FLAG (T3) - the status-label lookup expression

- Evidence: plan: `LISTING_STATUS_LABELS[status as ListingStatus] ?? status`;
  `flyerUnit.status` is `string` (`unitsRepo.ts:380`). It compiles (TS 5.9.3
  probe, strict + noUncheckedIndexedAccess) and lints clean (the config is
  not type-checked, so no no-unnecessary-condition). But the `??` is never
  needed for TYPES (the indexed type is `string`, not `string | undefined`),
  contrary to the plan's "keep it for type safety"; and an inherited key
  would yield a function - the repo's own picker `statusLabelFor` guards that
  with hasOwnProperty (`statusModel.ts:248-257`). The guard
  `isListingStatus(x): x is ListingStatus` exists (`statusModel.ts:456-458`).
- Readings: (a) the plan's cast + `??` (correct output for every reachable
  input; the fallback is dead code); (b)
  `isListingStatus(status) ? LISTING_STATUS_LABELS[status] : status` -
  cast-free, prototype-safe, same output.
- Recommendation: (b), importing `isListingStatus` and `LISTING_STATUS_LABELS`
  (no type import then needed). If (a) is kept, import the type as
  `type ListingStatus` (repo style; lint accepts either).
