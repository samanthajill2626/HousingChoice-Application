## GAPS — things this change breaks that the plan omits

**G1 — `relayGroups.ts` has no `sentBody` branch, so the "3 copies keep in sync" comment is already a half-truth, and Task 5's withhold makes it worse.** The Task 5 instruction "A SENT rung is untouched - its snapshot renders first, above this" is stated for `bodyFor` only. In `relayGroups.ts` there is no snapshot line at all (`:250-252` says so explicitly), so the withhold branch is unconditionally first. That is behaviourally fine today (pending-only filter) but means the three copies will now differ in **branch ORDER**, not just presence — and the DUPLICATED SHAPE comments the plan asks to "update … to name BOTH '' rules" will describe a rule one copy cannot have.

**G2 — `contactTimeline.ts` gathers reminders for MULTIPLE tours with DIFFERENT `tourType`s, and the plan's `namesOnce` memo is keyed by `unitId` only.** The walk (`:886-899`) admits `self_guided` tours *and* non-self_guided tours with an unusable group. Two tours at the **same unit** with **different tour types** share one `namesOnce(unitId)` entry. `resolveTourContactNames` as specced takes `{tenantId, unit, …}` and no `tourType`, so the memo is probably safe — but `assessNamesReadFailure` takes `tourType`, and the plan stores the flags **inside** `UnitNames` (the memoized value). If a future resolver ever branches on tour type the memo silently cross-contaminates. Worth a comment at minimum; the plan says nothing.

**G3 — the no-show-draft handler gains a `settings` read that can now fail the route.** Step 8 adds `readQuietHoursWindow(settings, log)` to a handler that today does exactly two things: `tours.get` and `resolveMessage`. The plan's own note says `readQuietHoursWindow` never throws, so this is a **latency/cost** regression rather than a correctness one — but `toursApi.test.ts`'s existing draft tests use `makeWebhookHarness()` and were never written to provide a settings repo for this route. Unverified whether the harness's default `settingsRepo` is wired on this mount; if not, the route now default-constructs a DynamoDB `SettingsRepo` in unit tests.

**G4 — Task 5's 409 on the no-show draft has no consumer contract on the ERROR side of the existing test.** `toursApi.test.ts:1510` is `it('404s for an unknown tour (mirrors the reminders route)')`. Adding a 409 gives the route three terminal shapes (`200 {body}`, `404 {error:'tour_not_found'}`, `409 {error:'names_unavailable'}`) where the docblock at `:539-541` claims only two ("a bogus id is a client error, not a 200 with the template"). The plan updates the docblock for the composer change but not for the new refusal.

**G5 — `resolveTenantSuppression` containment changes the OBSERVABLE chip for group-routed tours too, silently.** Task 5's fix (leave `suppressionOf` unassigned on a throw) is correct for the ternary, but there is a second consumer of the estimate: the GET response's log line at `:510-518` (`suppressed: reminderViews.some((v) => v.suppression !== undefined)`). Under containment a contacts blip flips that field from `true` to `false` with no other signal beyond the one new warn — an operator reading logs sees "no rung suppressed" during an outage. One extra log field would fix it; the plan doesn't mention the log line at all.

**G6 — the PATCH/send-now echoes will pay for a contacts read on EVERY cancel/restore click.** Today `addressOf` is one unit GetItem. `composeInputsOf` makes it unit + 1–2 contact reads, on a handler whose entire purpose is a state echo whose body the panel largely already has. The plan's batching rule (spec 10) is about the *timeline*; nobody costed the PATCH path. With the panel refetching on `scheduled.updated`, a cancel now triggers: PATCH (unit+contacts) → SSE → GET list (unit+contacts+tenant-suppression contacts, i.e. the acknowledged double read). That is 5+ reads per click where there are 2 today.

**G7 — `viewOf`'s docblock (`:262-265`) becomes wrong.** It says "The body is resolved ONCE per request by the handler and passed IN: composing needs async unit/settings reads, and this projection is sync." After Task 4 it also needs async *contact* reads. Not in the plan's list of docblocks to update (it names `composeBodyForRow`'s header, `RunDueTourRemindersDeps.unitsRepo`, and the draft route's docblock).

**G8 — nothing in the plan addresses `TourRemindersRouterDeps.unitsRepo`'s docblock (`:91-95`)**, which currently reads "ONE unit read, TWO consumers … roster resolution for the send-now path's D11 check … and the unit's address". After this change it has THREE consumers (address, roster, property-contact resolution) and — per the Task 5 carve-out — a failed read can now BLOCK a send for `en_route` on a non-self_guided tour, which directly contradicts "never blocks a send" reasoning mirrored here from `jobs/tourReminders.ts:371-374`. The plan updates the jobs-side twin and not this one.

**G9 — `api.ts:818` forwards `contactsRepo` only when injected, but `relayGroups` uses a SEPARATE dep name.** `api.ts:966-968` wires relay's contacts from `deps.contactsRepoForRelay` first, falling back to `deps.contactsRepo`. Any new test that injects a throwing contacts repo to exercise `names_unavailable` on the relay bucket must know to use `contactsRepoForRelay`, or it will silently exercise a real/other repo. Not mentioned anywhere in the plan's test steps.
