# Backend research: AI contact-kind suggestions

## Live baseline and contract

- The mission is pre-implementation. `rg classification_revision|contactClassificationRevision app/src app/test` has no live hits. The present `typeSuggestion` union is exactly `'tenant' | 'landlord'` in `app/src/adapters/extraction.ts:73-87`; it must become the one shared four-value `SuggestedContactKind` type before any runtime activation.
- `ContactType` remains exactly `'tenant' | 'landlord' | 'partner' | 'team_member' | 'unknown'` (`app/src/repos/contactsRepo.ts:45-52`). Property Manager is not and must not become a member; it is stored as `type: 'landlord'` plus an exact `role: 'Property Manager'`.
- The classification invariant is currently unenforced: `ContactsRepo.update()` sends a single unconditioned `UpdateCommand`, condition only `attribute_exists(contactId)`, with `SET`/`REMOVE` built from the patch and `ALL_NEW` return (`app/src/repos/contactsRepo.ts:1152-1211`). This is the sole repository mutation owner to extend with an atomic `if_not_exists(classification_revision, 0) + 1` whenever a supplied `type` or `role` field (including `role: null`) changes the stored kind.

The fake reads the first newest client `EXTRACT:` marker as `Partial<ExtractionResult>` and returns `{ fields: {}, ...partial }` (`app/src/adapters/extractionFake.ts:67-111`); widening the shared result type widens this typed e2e seam without a protocol change.
2. The schema currently has `typeSuggestion.value` enum `['tenant', 'landlord', 'none']` (`app/src/services/extraction/schema.ts:119-128`) and `parseExtractionText()` accepts only `tenant|landlord` (`:242-251`). `parseExtractionOps()` deliberately treats any nonempty non-`none` string as an attempted suggestion (`:420-429`), so it must remain stringly for off-enum audit evidence.
3. The old prompt frames `client` as a housing seeker (`app/src/services/extraction/prompt.ts:14-17`) and permits only Tenant/Landlord while suppressing a caseworker type suggestion (`:65-69`). The task must replace this semantic block, not alter transcript wire labels or the raw payload fingerprint algorithm (`:102-118`).
4. `applyExtraction()` is the Unknown-only type writer. It calls `putSuggestion({ target: 'type', currentValue: contact.type, suggestedValue, conversationId, tsMsgId, runId })`, records `suggested`, and otherwise records `type_already_classified` (`app/src/services/extraction/apply.ts:534-576`). Its current `ApplyDeps` has only `contacts.update|addPhone|findByPhone` and `extraction.putSuggestion|deleteSuggestion|hasDismissal` (`:34-44`); Task 3 must add `contacts.getById` plus the revision-fenced deletion method. A successful temporary put currently causes the final `suggestion.updated` once via the `wrote + suggested + notedLines` condition (`:697-702`), so the post-put retract needs a separate state-change flag.
5. The extraction job calls `applyExtraction()` only after `aiRuns.beginFinalization()` (`app/src/jobs/extraction.ts:567-596`), builds decisions from raw operations and apply decisions (`:583-588`), and later calls `putRun()` (`:602-633`). `AiRunsRepo.setVerdict()` is marker-safe: it tries a live run, then the `inflight#` marker, then fallback marker creation (`app/src/repos/aiRunsRepo.ts:400-477`). This is why an extraction-side losing delete must retain its `suggested` decision: route-owned terminal marker verdicts must merge during `putRun` rather than be overwritten as `not_presented`.
6. Real construction sites are the worker `applyDeps` (`app/src/worker.ts:458-494`) and the hermetic dev tick (`app/src/routes/dev.ts:643-691`). Both already hand the real contacts/extraction repositories through and should only need typed interface compatibility after Task 3.

## Suggestion persistence and exact identity

- A pending row is `sugg#<contactId>#<target>` with by-owner and by-pending indexes (`app/src/repos/extractionRepo.ts:81-107`, `:228-233`). Fields are `ownerContactId`, `target`, `suggestedValue`, optional `currentValue`, `reason`, `conversationId`, `tsMsgId`, `runId`, immutable `revision`, and `createdAt`. Add optional `contactClassificationRevision` only to this row shape; do not change public list/Today contracts.
- `putSuggestion()` makes a fresh `revision: randomUUID()`, preserves the generic latest-wins replacement policy under a dismissal+CAS transaction (`app/src/repos/extractionRepo.ts:489-614`). Copy the optional source contact revision into its constructed `item` without changing that replacement behavior for any target.
- Present identity conditions are revision-first, then legacy `createdAt` plus present/absent `runId`, in `deleteSuggestionIfCurrent()` (`app/src/repos/extractionRepo.ts:667-694`); this exact policy is also mirrored in `putSuggestion()` replacement conditions (`:532-562`). Export one `sameSuggestionIdentity` helper with the same precedence, then build the new type-only cross-table transaction from it.
- `getSuggestion()` is currently eventually consistent and takes no options (`app/src/repos/extractionRepo.ts:617-622`). Add `opts?: { consistentRead?: boolean }`; `listSuggestionsByContact()` and `listPending()` remain generic GSI readers (`:624-634`, `:711-739`).
- The new guard must use `TransactWriteCommand`: contacts table `ConditionCheck` and exact suggestion `Delete` in one transaction. Logical revision zero requires physical `attribute_not_exists(classification_revision) OR classification_revision = 0`; later revisions require exact numeric equality. On cancellation, consistently read both rows and report `deleted | suggestion_changed_or_absent | contact_revision_changed`, in that diagnostic priority.

## Human classification writer and downstream consumers

- `PATCH /api/contacts/:contactId` is the only human classification endpoint (`app/src/routes/contacts.ts:1386-1700`). `parseTriageBody()` already puts a supplied role into the patch and represents empty role as `null` (`:634-639`). It snapshots every changed-field suggestion before `contacts.update()` (`:1506-1527`), deletes the same exact row afterward, and stamps a type verdict only by comparing `parsed.patch[f]` to the suggestion (`:1529-1558`). This misses role-only edits, cannot distinguish Property Manager from Landlord, and intentionally leaves replacements created during the update pending.
- Keep generic cleanup for all non-type fields. For any PATCH carrying `type` or `role`, take a best-effort consistent prewrite type snapshot, update the contact, then boundedly reread/drain only older-revision `target: 'type'` rows with the new guarded delete. Reuse the existing single `verdictAt` binding. A prewrite identity gets `accepted` only if complete resulting kind matches; postwrite replacements get `superseded_by_human_edit` regardless of value; rows without `runId` delete safely but cannot be stamped.
- Existing route side effects must remain attached to this PATCH: Tenant -> onboarding, Landlord -> interested, Partner -> active (`app/src/routes/contacts.ts:1426-1444`); only linked `unknown_1to1` conversations flip (`:1633-1649`); only Tenant schedules triage extraction (`:1651-1671`). Property Manager therefore uses the existing Landlord behavior naturally once the patch has `{ type: 'landlord', role: 'Property Manager' }`.
- Generic suggestion accept must remain refused for type (`app/src/services/suggestionResolution.ts:203`); type rows are reviewed via PATCH only. GET suggestions reads the generic pending list and recovery surface (`app/src/routes/suggestions.ts:93-107`). Today groups `listPending()` rows by contact, so a stale type row remains visible until its deletion (`app/src/routes/today.ts:942-973`).
- Dashboard/API readers to protect: `useSuggestions` sends immutable revision/createdAt/runId identities (`dashboard/src/routes/contact/useSuggestions.ts:78-107`); `UnknownFile` currently displays raw `capitalize(suggestedValue)` and only Tenant/Landlord actions (`dashboard/src/routes/contact/UnknownFile.tsx:81-119`); existing display ownership is `PM_ROLE = 'Property Manager'` and `displayKind()` role-first (`dashboard/src/routes/contact/contactProfile.ts:9-33`); the AI run decision ledger presently renders `proposedValue` raw while raw panes intentionally remain exact (`dashboard/src/routes/settings/aiRuns/AiRunDetail.tsx:45-69`).

## Complete mutation/read surface for the classification fence

- New contact/stub writers: direct create through `ContactsRepo.create/createIfAbsent` (`app/src/repos/contactsRepo.ts:535-570`); automatic unknown capture (`app/src/services/contactCapture.ts:79`), group conversion (`app/src/services/groupConvert.ts:339`), group-member discovery (`app/src/services/groupMembers.ts:111`), and seed documents (`app/src/lib/seed/cast.ts`, `app/src/lib/seed/lean.ts`). They must stay revision-absent; no migration, seed, import, capture, or backfill change is warranted.
- Only `ContactsRepo.update()` changes an existing contact's `type`/`role` in production; all direct backend edits and dashboard writers funnel through the PATCH route. Extraction does not and must not write either field.
- Readers/renderers affected by a changed type/role: extraction eligibility and profile (`app/src/jobs/extraction.ts:131-158`, `:435-448`), PATCH status/conversation propagation above, suggestions/Today above, dashboard profile/Unknown file above, plus existing Tenant/Landlord/Partner file selection through ContactDetail. Classification revision itself is internal: only contacts repo update returns it and extraction/contacts reconciliation should inspect it.

## Live-tree deviations / risks

1. No substantive spec drift found: the approved task order matches the live baseline, and activation is correctly delayed until schemas, parser, prompt, persistence, PATCH, and UI can all honor the new values.
2. Highest risk is ownership during finalization: treating an absent/replaced row as an extraction-side drop loses a route marker verdict. Only a successful extraction-owned guarded delete may produce a dropped decision.
3. Highest route risk is retaining the generic `parsed.patch.type` equality check. It cannot classify Property Manager, role-only edits, custom roles, or a replacement published after the write; special type cleanup must be separated from generic field cleanup.
4. The current in-memory harness intentionally mirrors generic identity but has no revision semantics; without updating it and the three typed repo stubs, focused tests can compile yet miss the production transaction/race contract.
