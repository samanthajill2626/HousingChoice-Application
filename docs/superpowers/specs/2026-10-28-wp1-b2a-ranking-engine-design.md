## 1. Goal

Given one anchor (a property or a tenant), B2a computes its pool, builds
one card per record, asks the model for an absolute score and short
reasons for every candidate, applies the Weak cap and the fair-housing
flags in code, and stores one match per tenant-property pair. Opening a
page reads stored matches and says which are out of date; only a press
of Rank (or Update) calls the model. The only new screen is the admin
Rankings page, where a ranking can be run and every run, its cost and
its pairs inspected, so the engine runs in production before B3's
composer. Deploying B2a turns ranking on (no switch, charter item 12), so
the counterfactual fair-housing check is B2a's merge gate.

B2a also carries three small Notes-box changes Cameron folded in
(2026-10-28): line breaks in a model Notes line are collapsed, the retry
guard's drops are counted, and the contact edit form's Notes save gets
the Staff notes stale-save guard.

## 3. Decisions

### D1. The pool (charter 5)

One module, `app/src/services/ranking/pool.ts`, computes the pool for an
anchor at the moment it is called. It is called by the job when it runs
(the pool scored is the pool at run time) and by the read (D9).

Property anchor (candidates are tenants):

- Tenants with `status = 'searching'`, read through
  `contacts.listByType('tenant', { status: 'searching' })` paged to the
  end (that read already excludes soft-deleted contacts).
- Sendable: not `sms_opt_out`, not `sms_unreachable`, has a phone; the
  same three tests audienceResolution.ts:197-199 applies. SMS consent is
  NOT a pool rule: each candidate carries `hasConsent`
  (`hasSmsConsent`, lib/smsCompliance.ts:101) for B3/B4 to show.
- Voucher size: the unit's sizes come only from `acceptedVoucherSizes`,
  clamped to 0-4 and de-duplicated exactly as the composer prefill does,
  and are compared with the existing server twin (`voucherSizeMatches`
  over `bedroomSizesOfFilter`), so 4 means 4 or more. A tenant with no
  voucher size never matches a non-empty list; a unit with neither sizes
  nor beds takes every size.
- Housing authority: `authoritiesOf(unit)` mapped through a NEW server
  function `mapAuthoritiesToList(names, orgEntries)` in
  app/src/lib/orgNames.ts that ports `prefillAuthorities` /
  `settleTypedOrgText` exactly, ambiguity rule included, and returns
  `{ mapped, unmapped }`. A parity test runs the dashboard's own prefill
  cases against the port. The tenant's `housingAuthority` must equal one
  mapped name after `normalizeOrgText` on both sides (case and spacing
  folded, never fuzzy; Cameron's standing rule). No recorded authority:
  every authority. Recorded but none mapped: not limited. Some mapped:
  limited to the mapped ones. Unmapped names feed the completeness pass
  (D3). The org list is read once per pool with
  `createOrgNamesService().read()`; if the read fails the pool fails and
  the ranking fails with a message; it never runs unlimited.
- Recency: `last_heard_from_at` within `RANKING_POOL_WINDOW_DAYS`
  (default 90, positive integer, fail-fast). Never heard from: counts from
  `created_at`, except a contact carrying `imported_from`, which never
  uses that fallback (charter 5). The window is lifted when the request
  says `includeOlder: true`.

Tenant anchor (candidates are properties):

- Units with `status = 'available'` (`unitsRepo.listByStatus`, deleted
  excluded) and no active placement for a different tenant. B2a adds
  `placementsRepo.hasActivePlacementForOtherTenant(unitId, tenantId)`
  (reads `listByUnit`, pages to the end). Pools are small (22 live
  available units in production), so one read per unit is accepted.
- The size and authority rules above, read from the property's side with
  the anchor tenant's size and authority.

Any record can be the anchor. The pool result carries
`anchorNotes: ('not_searching' | 'not_sendable' | 'not_available')[]`
for the banner B3/B4 build; the Rankings page shows them as text. Ranking
is never refused for the anchor's state.

A safety ceiling, `RANKING_MAX_POOL` (default 300): a pool above it fails
the ranking with "Pool too large to rank (N candidates)". It removes no
candidate; it bounds the cost of one press (the window-off property pool
was 158 at worst in production; charter 2). Q3.

### D2. The cards (charter 6.1-6.3)

#### D2.1 Classification as code

`app/src/services/ranking/cardFields.ts` holds two registries,
`TENANT_CARD_FIELDS` and `PROPERTY_CARD_FIELDS`, each a record from a
stored attribute name to either `{ use: 'include', label }` or
`{ use: 'exclude', reason }` (the reason is a short charter citation).
The card functions in `cards.ts` build a card by iterating the STORED
record's own keys and copying only keys classified `include`, so every
legacy, tombstoned or new attribute is dropped until someone classifies
it (charter 6.1: an allowlist at runtime).

Tenant card, included: `firstName`, `lastName` (names stay, charter 7.2),
`address` (whole), `voucherSize`, `housingAuthority`, `porting`,
`tenure`, `pets`, `evictions`, `status`, `voucher_expiration_date`,
`customFields`, `created_at` (as a date), `notes` (arranged, D2.3),
`staff_notes`, and every key named in B1's `TENANT_MATCHING_INPUTS` whose
source is `field` (read from that list, never spelled out, so a source
moving to Notes changes one list; B1's reader test keeps policing it).
Derived and added: `lastHeardFrom` as a bucket (this week = under 7 days,
this month = under 30, one to three months = under 90, older, never;
charter 9.1) and `propertiesSeen` (D2.3).

Tenant card, excluded (reason in the registry): ids and refs
(`contactId`, `phone_ref*`, `email_ref*`, `quo_contact_ids`), phones and
emails, `lifEligible` (income, A1), `relationships` (other people),
consent fields, opt-out and unreachable flags, `status_source`,
`park_reason`, `deleted_at`, capture and origin fields, import
bookkeeping (`imported_from`, `imported_at`, `display_name`),
`classification_revision`, `type`, `type_source`, `organization`,
caseworker fields, `last_heard_from_at` and `last_reached_out_at` (the
bucket replaces the first), `staff_notes_updated_at`, `notes_updated_at`
(D14), public sign-up bookkeeping (`unit_of_interest`,
`housing_fair_*`; a flyer sign-up already reaches the card through
properties seen), and every landlord-only or partner attribute
(`req_*`, `contract_status`, `registered_landlord`, `rta_within_48h`,
`pass_inspection_first_try`, `income_includes_voucher`, `company`,
`agency`, `role`, `expected_rent`, `accepts_programs`, `lease_terms`,
`pet_policy`), which a tenant record does not normally hold.

Property card, included: `address`, `beds`, `baths`, `area`, `subzone`,
`rent_min`, `rent_max`, `final_rent`, `payment_standard`, `deposit`,
`deposit_one_month`, `deposit_flexible`, `deposit_notes`,
`application_fee`, `same_day_rta`, `utilities`, `accessibility`, `notes`,
`lease_terms`, `pets`, `pet_fee`, `no_pets`, `no_evictions_on_program`,
`evictions_notes`, `qualifications`, `tour_type`, `tour_process`,
`application_process`, `washer_dryer`, `status`, `created_at` (date).
Derived: `voucherSizes` from `acceptedVoucherSizes` with
`voucherSizesInferredFromBeds: boolean`, and `authorities` as
`{ mapped, unmapped }` (D1).

Property card, excluded: `priority` (charter 9), `credit_requirements`
and `income_requirements` (A1), `lif` (Q4: an income-program attribute,
excluded with the tenant's `lifEligible`), ids (`unitId`, `landlordId`,
`propertyId`), `contacts`, `primary_contact` (other people), `media`,
`listing_link`, `video_url`, `requirement_sources`, `status_source`,
tombstones (`jurisdiction`, `accepted_programs`), import bookkeeping,
legacy `bedrooms` / `bathrooms`, `deleted_at`, `updated_at`,
`voucher_size_accepted` and `accepted_authorities` (replaced by the
derived forms).

Landlord card switch `RANKING_LANDLORD_CARD` (default `false`, boolean,
fail-fast): when on, the property card gains `landlordDefaults`: the
landlord of record's (`landlordId`) requirement values read through
`landlordItemValue`, credit and income items left out, plus the
landlord contact's `notes`, labeled as the landlord's defaults. An item
the property records its own value for is left out of the defaults
(the property's value wins). Off: nothing of the landlord's is read.

#### D2.2 Shape, order and size

A card is a plain JSON object with fixed key order (registry order), so
the same record always serializes to the same bytes. Free text is passed
as stored, except that each value is trimmed. The card holds no record
id: the call refers to candidates by handle (D5).

`cards.ts` exports `tenantCard(contact, ctx)` and `propertyCard(unit,
ctx)`; `ctx` carries the org list mapping, the clock, the landlord
record (switch on) and, for the tenant, the properties-seen inputs. Both
are pure; the job and the read gather the inputs.

#### D2.3 Properties seen and the Notes arrangement (the attach step)

The tenant card carries `propertiesSeen`, newest first, bounded to
`RANKING_SEEN_MAX` (default 8) entries. Sources: every listed
`listing_sends` row for the tenant (`listByContact`, so `counted` and the
legacy `sentAt` fallback follow `isListed`), with each share told apart as
"sent" or "signed up" (the `flyer` share key), plus the tenant's tours
(`toursRepo.listByTenant`). Each entry reads as one unit:

- `label` (`propertyLabel`) and a SHORT summary of that property: beds,
  baths, rent (range or final), area, subzone, voucher sizes, pets
  policy. Not the whole property card: a property ranking carries up to
  40 tenant cards per call and eight full property cards each would
  multiply the input several times over (Q2).
- `sends`: each date with its kind (sent, signed up), and
  `daysSinceLastSend`.
- `declined`: `{ by, at }` when set (the stored record, never the
  derived outcome).
- `tours`: each tour's status, outcome and dates.
- `feedback`: the Notes lines that name this property.

The attach step lives alone in `app/src/services/ranking/seenFeedback.ts`
so WP3 can delete it (charter item 8, issue
wp3-property-feedback-redesign): it splits the Notes box into physical
lines, and a line that `labelMatches` a seen entry's label goes under
that entry (under each entry it matches) and is left out of the card's
`notes`; every other line stays in `notes` and bears on every property.
Whole lines move, staff-typed lines included, as charter 6.2 says (Q1).
No other polish: no abbreviation folding, no date parsing of the
`[Auto - <date>]` prefix (it has no year; age comes from stored dates).

A seen unit that cannot be read (deleted or missing) is still listed by
its last label if the send row is all there is: the entry keeps its
sends, decline and tours with `label: "a property no longer on file"`;
its feedback lines cannot attach and stay in `notes`.

#### D2.4 The classification test

`app/test/rankingCardFields.test.ts` fails when a stored attribute is
neither included nor excluded. Because both item types carry an index
signature, it checks three sources:

1. Type level: the registries are typed
   `Record<KnownKeys<ContactItem>, ...>` / `Record<KnownKeys<UnitItem>, ...>`
   plus the untyped keys (KnownKeys strips the index signature), so a new
   typed attribute does not compile until classified.
2. Writer keys: the attributes each writer stores that are not typed - the
   contacts PATCH and create parsers' accepted keys, the importer's
   contact and unit attribute lists, public sign-up's, the units PATCH
   `WRITABLE_FIELDS` - are imported (or, where a writer has no exported
   list, pinned by a source-text scan as `tenantMatchingInputsReaders`
   does) and asserted classified.
3. Seed world: every attribute on every tenant and unit of the `full` and
   `lean` seed worlds is asserted classified.

A second test asserts the runtime allowlist: a record carrying an
unclassified attribute produces a card without it.

#### D2.5 Pair history (charter 6.3)

Per candidate, scoped to THIS tenant and THIS property, from stored
facts: every counted send date with its kind (sent or signed up), the
declined record with who and when, the tours between the two (status,
outcome, dates), and `daysSinceLastSend`. The derived outcome is never
used.

### D3. The completeness pass (charter 7.3)

`app/src/services/ranking/completeness.ts` marks gaps against a fixed
list, each a stable key with a staff label:

- Property: `rent` (none of `rent_min`, `rent_max`, `final_rent`),
  `payment_standard`, `voucher_sizes` (none recorded; a size inferred
  from beds counts as missing), `authorities_unmapped` (any recorded name
  that does not map), `pets` (none of `no_pets`, `pets`, `pet_fee`),
  `accessibility`.
- Tenant: `voucher_size`, `housing_authority`, and each
  `TENANT_MATCHING_INPUTS` entry marked for completeness. B2a adds
  `completeness: boolean` to that list's entries: `true` for
  `area_preference` and `max_tenant_portion`, `false` for the other two
  (charter 7.3's list; the dashboard mirror and its drift test follow).

The flags go to the model with each card (as `missing: [labels]`) and
come back on the match as `missing[]`: the code flags first (with their
keys), then the model's own `unknowns` not already equal to a flag's
label (compared with case and spacing folded). Missing data never stops
a ranking.

### D4. The rubric, the worked examples and the prompt (charter 7.1, 7.2)

- `app/src/services/ranking/rubric.ts` exports `RUBRIC_VERSION` (`'r1'`)
  and `RUBRIC_TEXT`. A `.ts` module, not a Markdown file, so the
  compiled `dist/` carries it (the smoke gate proves imports resolve
  under plain Node). It states, in order: what a score means at the
  anchor points (100 nothing against and preferences met; 80 strong fit
  with minor compromises; 60 workable with a real compromise; 40
  unlikely; 0 cannot work) and that scores are ABSOLUTE, never relative
  to the other candidates in the call; how each input bears on fit; the
  cap rule for the cap-eligible requirement keys and that every other
  requirement and every decline is weighed, never forced (charter 4);
  the maybe rule (a staff Not interested together with feedback on that
  property saying the tenant was unsure reads as a maybe, a slight
  reason against that fades with time since the last send); fair housing
  (protected characteristics, sex including sexual orientation and
  gender identity, never lower a score; disability only for the tenant's
  benefit; credit and income in any field on either card are disregarded
  and never reported failed; rent, payment standard and the tenant's
  maximum portion are not credit or income); the two flag kinds,
  unlawful and accommodation, with examples (charter 7.2); that
  uncertainty is reported as `unknowns` and scored as uncertainty, not
  guessed away; and the reasons format (up to three for, three against,
  short phrases or single words, each with its source).
- `app/src/services/ranking/examples.ts` exports `EXAMPLES_VERSION`
  (`'e1'`) and about ten SYNTHETIC worked examples spread across the
  bands, including a capped pair, an accommodation pair (assistance
  animal against No pets), an unlawful-requirement pair, a maybe pair and
  a pair with missing inputs. Each is a short anchor card, candidate card,
  pair history and the expected output. Made-up people and addresses
  only. Cameron checks them at the handback; B2b asks Sam to glance at
  the bands. B2b's promotion grows the set; B2a only reads this file.
- The call: system = rubric then examples (byte-stable for a given
  pair of versions); user = the anchor card (with its missing flags),
  then each candidate as `{ handle, card, missing, pairHistory }` with
  handles `c1..cn` in pool order. `promptFingerprint` = sha256 of the
  system text, recorded on every run.

### D5. Output schema and parsing (charter 7.4)

Structured output through `output_config.format` (json_schema), all keys
required, no optional parameters, `additionalProperties: false`
everywhere, sentinels for none (empty arrays), exactly as extraction's
schema discipline. Shape:

```
{ candidates: [ {
    candidateId: string,
    score: integer,
    for:     [ { text: string, source: <source enum> } ],
    against: [ { text: string, source: <source enum> } ],
    unknowns: [ string ],
    failedRequirements: [ <requirement key enum> ],
    fairHousingFlags: [ { kind: "unlawful" | "accommodation",
                          field: <property card field enum> } ]
} ] }
```

- Source enum: `voucher_size`, `authority`, `rent`, `area`, `pets`,
  `evictions`, `accessibility`, `requirements`, `preferences`, `notes`,
  `staff_notes`, `feedback`, `history`, `recency`, `property_details`,
  `other`.
- Requirement key enum: the 15 `REQUIREMENT_UNIT_KEYS`.
- Flag field enum: every free-text field on the property card plus the
  requirement keys (and their landlord-default twins when the switch is
  on, as `landlord:<key>`).
- Named object nodes: the candidate, the reason (used twice) and the
  flag. B1's measurement was eight named objects compiled and twelve
  failed; this schema is far below it. An offline test
  (`app/test/rankingSchema.test.ts`, modeled on extractionSchema.test.ts)
  pins zero optional parameters, `additionalProperties: false`, no
  `minimum` / `maximum` / `minLength`, and AT MOST FIVE object nodes, so
  a later edit that grows the schema fails offline first. The real
  compile is still checked: `extraction-schema-compile-check.ts` gains a
  `ranking` variant (RUNBOOK "Changing a structured-output schema"
  gains the ranking schema), and Cameron runs it (D17).
- Parsing (`parseRankingText`), never throwing to the job: score clamped
  to 0-100 and rounded; `for` and `against` cut to three, each text
  trimmed and cut to 80 characters, empty texts dropped; `unknowns` cut
  to five; unknown enum values dropped. A candidate the model did not
  return, returned twice (every copy discarded) or returned under an
  unknown handle gets NO new match; a batch whose call failed (API
  error, refusal, truncation, timeout, parse failure) gets none for any
  candidate. A default or guessed score is never written (charter 7.4).

### D6. Drivers and configuration (charter 14)

- `app/src/adapters/ranking.ts` (the only new Anthropic SDK import) and
  `app/src/adapters/rankingFake.ts`. Interface:
  `RankingDriver { kind: 'anthropic' | 'console' | 'fake';
  rankBatch(input): Promise<RankingCall> }`; `RankingCall` is a
  discriminated result that never throws, as `ExtractionCall` is:
  `{ ok: true, meta, output }` or `{ ok: false, meta, failure:
  'refusal' | 'parse' | 'truncated' | 'timeout' | 'driver', message }`,
  `meta` holding model, raw text, usage and latency.
- Anthropic request: `model` = `AI_RANKING_MODEL` (default
  `claude-sonnet-5-5`); `max_tokens` = `RANKING_MAX_OUTPUT_TOKENS`
  (default 16000; thinking tokens count against it); `thinking:
  { type: 'adaptive' }`; `output_config: { effort: RANKING_EFFORT,
  format: { type: 'json_schema', schema } }` with `RANKING_EFFORT`
  default `low` (charter 14); request options `timeout:
  RANKING_CALL_TIMEOUT_MS` (default 120000) and `maxRetries: 1`, so one
  call's wall clock stays bounded. No server-side refusal fallback: a
  fallback would score some pairs on another model, breaking "one model
  per ranking" and the version rule (charter 10.3); a refusal is a
  failed batch.
- The thinking trap: the ranking driver accepts only models in a
  supported set (`claude-sonnet-5-5`, `claude-opus-5-5`; both run
  adaptive thinking with an effort); any other `AI_RANKING_MODEL` stops
  startup. The extraction driver's `thinkingOff` is not used here.
- `RANKING_DRIVER`: `anthropic` | `console` | `fake`, default
  `anthropic` in production and `console` otherwise; `fake` refused in
  production; validated as `EXTRACTION_DRIVER` is. `ANTHROPIC_API_KEY` is
  required in production when the ranking driver is `anthropic`, whatever
  `AI_EXTRACTION_ENABLED` says. `ANTHROPIC_API_BASE_URL` stays refused in
  production.
- Fake driver: deterministic scores from the cards with fixed rules and
  no network (start at 70; minus 25 per failed check it can read
  structurally - voucher size outside the property's sizes cannot occur
  in a pool, so it reads rent above the tenant's maximum portion, a
  recorded No pets with non-empty tenant pets text (failedRequirements
  `no_pets`), a recorded `no_evictions_on_program` with non-empty tenant
  evictions text; plus 10 when the area preference text appears in the
  property's area or address; one reason per rule fired). Test seams: a
  property or tenant whose notes contain `[fake:fail-batch]` makes every
  batch holding it fail; `[fake:omit]` omits that candidate;
  `[fake:unlawful:<field>]` raises an unlawful flag on that field. Used
  by every e2e spec and the hermetic stack.
- Console driver: logs the request size and the first candidates' cards
  at debug level, then scores with the fake rules and records driver
  `console` (so local dev without a key still ranks).
- Price table: `AI_PRICE_TABLE` in config, defaulting to
  `{ "claude-sonnet-5-5": { in: 2, out: 10 }, "claude-opus-5-5":
  { in: 4, out: 20 } }` dollars per million tokens, overridable by an env
  JSON value parsed fail-fast; a ranking model with no price stops
  startup, because every run records its cost. Cost =
  `in * inputTokens / 1e6 + out * outputTokens / 1e6`, rounded to
  1e-6 dollars, stored on the run.
- Prompt caching: off (charter 14). The run records
  `cache_read_input_tokens` when present, so a later measurement can
  decide.

### D7. The ranking job: claim, poll, lease, takeover (charter 10.2)

The job record lives in the AI runs table, one per anchor:
`itemId = rjob#<anchorKind>#<anchorId>` (`anchorKind` `unit` or
`tenant`). Fields: `anchorKind`, `anchorId`, `status` (`queued`,
`running`, `done`, `failed`), `generation` (uuid), `includeOlder`,
`requestedBy`, `requestedAt`, `correlationId`, `traceparent`,
`attempts`, `queuedExpiresAt`, `leaseExpiresAt`, `poolSize`,
`batchCount`, `batchesDone[]`, `failedBatches[]` (each `{ index,
candidateIds, failure }`), `message`, `runIds[]`, `startedAt`,
`finishedAt`, `expires_at` (now + `RANKING_PAIR_TTL_DAYS`, so the failed
batch list outlives every match it flags; charter 10.2), plus the sparse
index keys below.

- The claim (`POST .../rank`): one conditional put that succeeds when no
  record exists, or the record is `done` or `failed`, or it is `queued`
  past `queuedExpiresAt`. It writes `queued`, a new `generation`,
  `attempts: 0`, the request's correlation id and traceparent, and
  `queuedExpiresAt = now + max(4 x WORKER_POLL_INTERVAL_MS, 120 s)`. A
  press that loses the write reads the record: if its `includeOlder`
  equals the press's, the press JOINS it (202 with the current record,
  `joined: true`); otherwise it is refused, 409 `ranking_running`, "A
  ranking is running for this record. Try again when it finishes."
- Index keys (`byEntity`, sparse): a queued record carries
  `entityKey = rankjobs#queued`, `sortKey = requestedAt`; a running one
  `entityKey = rankjobs#running`, `sortKey = leaseExpiresAt`; done and
  failed records carry neither.
- The ranking poll (`runDueRankings`, its own `startPoll('ranking', ...)`
  in worker.ts, always started; there is no switch): each tick queries
  queued records oldest first and running records whose `sortKey` is
  before now, and takes up to `RANKING_MAX_CONCURRENT_JOBS` (default 2)
  per worker process.
  - Claiming a queued record: conditional update `status = queued AND
    generation = :listed` to `running`, `startedAt`, `leaseExpiresAt =
    now + RANKING_LEASE_MS` (default 90000).
  - Takeover: a running record past its lease with `attempts < 1` is
    re-claimed with a NEW generation, `attempts + 1`, and run again from
    the start (once: enough to cover a redeploy). A second expiry marks
    it `failed` with "The ranking stopped before it finished. Press Rank
    again." A new press clears it.
  - Lease renewal: while a job runs, a timer every
    `RANKING_LEASE_MS / 3` extends the lease with a conditional update on
    the generation; a renewal that fails stops the job.
- Context: each job runs inside `runWithContext` restoring the record's
  `correlationId` and `traceparent`, so the job's logs and spans join
  the press that queued it.
- The generation check: before every model call and every write
  (match, run, flag, record), a consistent read of the record; on a
  different generation the job exits quietly. The check is not atomic
  with the write after it; a superseded job can still write the batch
  it had in flight, and the newer job rewrites every pair (accepted,
  charter 10.2).
- The run: compute the pool (D1) and the cards (D2), split into batches
  of `RANKING_BATCH_SIZE` (default 40, charter 7.1) in pool order, run
  batches in parallel up to `RANKING_BATCH_CONCURRENCY` (default 4),
  each with the per-call timeout. Each batch, as it finishes, writes its
  run (D11), its matches (D8) and its unlawful flags (D10), then appends
  its index to `batchesDone` (or to `failedBatches`) and emits the event
  (D12). When every batch has finished: `done` (with or without failed
  batches) and `finishedAt`. A pool of zero is `done` with no batches.
- Never throws: a model, batch, pool or organization-list failure is
  recorded on the record (`failed` with `message` when the job cannot
  run at all; a failed batch otherwise) and the job finishes. The
  attempt count lives on the record, as extraction counts.
- One job in flight per anchor (the claim). Background and scheduled
  ranking stay out (charter 10.2); `rankAnchor(anchor, opts)` is one
  function so a later scheduled caller is configuration.

### D8. The matches store (charter 10.1)

`app/src/repos/matchesRepo.ts`, the first repository on the `matches`
table. Row per tenant-property pair: `tenantId`, `unitId`, `schema: 2`,
`score`, `for[]`, `against[]`, `missing[]` (`{ key?, text }`),
`failedRequirements[]`, `fairHousingFlags[]` (the pair's flags as the
model returned them), `stage: 1`, `rubricVersion`, `examplesVersion`,
`model`, `runId`, `jobGeneration`, `computedAt`, `anchorSide`,
`fingerprints: { tenantCard, unitCard, pairHistory }`, `inputSnapshot`
(D8.1), `expires_at` (`computedAt` + `RANKING_PAIR_TTL_DAYS`, default
180). Not stored: band, cap state, priority effect, chips, sort
position; all derived on read.

- Writes: `putMatches(rows)` as BatchWrite, unprocessed items retried
  with backoff; a write that still fails is recorded as the batch's
  failure (its candidates get no new match and read as out of date).
- Reads: `getPairs(keys, { requireComplete: true })` by key from the base
  table, consistent; an unprocessed key throws rather than reading as
  "no match" (the batch-read ambiguity rule). The read (D9) uses this
  for every pool member in both directions, so it never depends on the
  eventually consistent `byUnit` index. `listByUnit` and `listByTenant`
  exist for the Rankings page only.
- A row without `schema: 2` is ignored by every reader. The lean seed's
  legacy row (lean.ts:445-457) is replaced by one `schema: 2` row for the
  same pair, scored by the fake rules with current versions and
  fingerprints computed from the seeded cards, so the hermetic world
  opens with one stored match.

#### D8.1 The input snapshot (the seam for B2b)

Each row carries `inputSnapshot`: the exact JSON that pair was scored
from (the anchor card and the candidate card as sent, with their missing
flags, and the pair history), gzipped and base64-encoded, plus
`promptFingerprint`, `rubricVersion` and `examplesVersion`. B2b copies it
into a review record when Sam reviews the pair (charter 12), and its
evaluation script re-scores from it. Each run also stores the whole
batch's user message gzipped (D11). B2a writes these; nothing in B2a
reads them except the Rankings page's run detail and tests.

### D9. Reading a ranking (charter 10.3, 8, 9)

`GET /api/rankings/:anchorKind/:anchorId?includeOlder=` (admin and va)
returns:

- `anchor`: display (name or label), `anchorNotes` (D1), its missing
  flags (D3), and `cardChanged` when any stored match's anchor-side
  fingerprint differs from the current anchor card.
- `job`: status, `batchCount`, `batchesDone`, `failedBatches`, `message`,
  `generation`, or `null`.
- `rows`: one per pool member: candidate id and display, `hasConsent`
  (tenants), `priority` (properties; read here, never sent to the
  model), and either `match: null` (`notRankedYet`, or `notScored` when
  the anchor's last job listed it in a failed batch) or the match with
  derived `band`, `capped`, `capReason`, and `outOfDate:
  ('card' | 'pairHistory' | 'age' | 'version' | 'failedBatch')[]`.
- `flags`: open unlawful flags for the properties in view (D10).

Derivations, all in `app/src/services/ranking/readRanking.ts`:

- Band from score: Strong 80-100, Good 60-79, Possible 40-59, Weak 0-39,
  constants in `bands.ts` (charter 8).
- Cap (charter 7.4): capped when `failedRequirements` holds a
  cap-eligible key (`no_evictions_on_program`, `evictions_notes`,
  `qualifications`, `no_pets`, `pets`) that is recorded on that
  property's current card, is not in the pair's accommodation flags, and
  has no open unlawful flag on that property. A capped pair reads band
  Weak, `capReason: 'requirement not met'`.
- Out of date: a fingerprint differs (tenant card, unit card, pair
  history; D2, D13), `computedAt` older than `RANKING_MAX_AGE_DAYS`
  (default 7), a rubric version, examples version or model other than
  current, or the candidate was in a failed batch of the anchor's last
  job.
- Sort (charter 9.2): property anchor - band, then score, then last
  heard from (falling back to `created_at`); tenant anchor - band after
  the priority strength (`RANKING_PRIORITY_STRENGTH`: `within_band`
  default, `one_band_up`, `always_first`), then priority on before off,
  then score, then property label. No priority lift or priority tie
  preference for a capped pair, which sorts last within Weak. Members
  with no match sort last.
- The read computes the current pool and cards (the out-of-date test
  needs them). The candidate card reads (sends, tours, units) run with a
  bounded concurrency (`RANKING_READ_CONCURRENCY`, default 16). The plan
  measures a 150-tenant property read on the hermetic stack; the window
  keeps the typical pool near 50.

### D10. Unlawful flags as property records (charter 7.2)

In the AI runs table: `itemId = uflag#<unitId>#<field>`, `unitId`,
`field`, `textHash` (sha256 of the field's trimmed text when raised),
`reason` (the model's against-reason or unknown text naming it, else
"flagged as a requirement fair housing does not allow"), `runId`,
`raisedAt`, index keys `entityKey = uflags#<unitId>`, `sortKey = field`,
no TTL. Dismissal fields are reserved (`dismissedAt`, `dismissedBy`,
`textAtDismiss`); the admin Dismiss and its display are B4's.

- Raised: unlawful flags are merged across a job's batches by property
  and field; a batch writes a flag record when none is open for that
  property and field (an open one keeps its first raising run).
- Open: the field's current text still hashes to `textHash`. Closed on
  read when it does not (the text was edited); no unit writer knows about
  flags. A closed record is overwritten if the model raises the flag
  again.
- While open, that field caps no pair of that property (D9), including
  pairs where the model missed it.
- Accommodation flags stay on the pair's match only.

### D13. Fingerprints (charter 10.3)
