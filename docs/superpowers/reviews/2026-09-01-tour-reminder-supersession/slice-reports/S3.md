### 1a. ADDITION: two counterweights the worklist did not name

- **timeless CREATE writes NO pointer.** The only case in the new describe that
  was GREEN before the implementation - which is the point: it proves the
  201/store assertions elsewhere are not satisfied by "always write something".
  An empty-string or always-present pointer would fail it, and D3 makes ABSENT
  mean pre-migration permanently, so the negative case is load-bearing.
- **status-only REVIVAL re-points** (`canceled` -> `scheduled` with no
  `scheduledAt`). The worklist's re-arm cases are all time-changes; the revival
  arm is the one that reaches `rearmTrigger` through `patch['status']` instead,
  and it is also the one that meets a tour whose pointer was rotated to an
  unmatched value by the earlier cancel. It exercises S1's fourth CAS cell
  (rotate-then-compare over a value no row carries) through the route.

### 1b. `terminal` is now a named const

Research B says the four terminal statuses are "enumerated there and NOWHERE
else on this route". The rotation decision needs the same predicate ABOVE the
write, so rather than duplicate the four-way disjunction I named it
`const terminal = ...` in the hoisted block and the `else if` became
`} else if (terminal) {` with its comment intact. Still exactly one enumeration.

### 1c. `rotation` is minted unconditionally

`const rotation = randomUUID();` runs on every PATCH; it reaches the store only
when `(armable && rearmTrigger) || terminal`. Minting it conditionally would type
as `string | undefined` and force a non-null assertion at the compare-and-set
(gate 5 territory) for no behavioral gain. Documented at the declaration.

## 5. THE SHIPPED BEHAVIOR CONTRACT for S4-S9

### Who writes the pointer, and when

| path | what happens to `currentLadderId` |
| --- | --- |
| `POST /api/tours` WITH `scheduledAt` | arm, then `tours.patch(tourId, { currentLadderId: ladderId })` when `ladderId !== null`. The 201 body is the patch's ALL_NEW return. |
| `POST /api/tours` timeless | nothing written. The attribute stays ABSENT (pre-migration shape, D3). |
| `PATCH` re-arm (`armable && rearmTrigger`) | rotation rides the `:1164`-equivalent patch write; cancel (unchanged); arm; `setLadderIdIf(tourId, rotation, ladderId)`. Won -> response spliced to `ladderId`. Lost -> `tours.get` re-read, response carries the WINNER's pointer. |
| `PATCH` terminal (`canceled`/`closed`/`toured`/`no_show`) | rotation rides the same patch write and is FINAL. No arm, no CAS, no sweep. `cancelTourReminders` still runs, unchanged. |
| `PATCH` anything else | the pointer is not touched at all (`patch['currentLadderId']` is never set). |

Invariants S4-S9 may rely on:

- The pointer is NEVER cleared and never written empty; the only two values it
  can hold are a `randomUUID()` rotation or an armer-minted `ladderId`.
- Post-S3, a tour created through the API and left `scheduled` ALWAYS satisfies
  `every armed row.ladderId === tour.currentLadderId`. **Any test that arms for
  real against a HAND-WRITTEN tour row still violates it** - that is the S6
  fixture hazard (worklist D#1.4), and it is now reachable from `toursApi`'s
  world too.
- The response body of both write paths carries the pointer that is in the
  store, in every branch including the lost CAS.
- Rotation is decided from `effectiveStatus` (`patch['status'] ?? currentStatus`),
  so booking/revival auto-advances rotate correctly; the body's `status` alone
  never decides.

### The three log messages (exact strings, ASCII, all at level 50)

```
tour reminders: pointer write failed after arming - the new ladder is unpointed
tour reminders: arm failed after pointer rotation - tour is DISARMED until the next reschedule
tour reminders: pointer write lost a concurrent reschedule - this ladder is unpointed
```

Bindings: `{ err, tourId, ladderId }` / `{ err, tourId }` / `{ tourId, rotation, ladderId }`.

Error posture, matched to the handler's existing behavior and NOT invented:

- CREATE-path pointer-write failure -> logged, **swallowed**, the 201 still
  lands (the arm is a documented best-effort side effect and the tour row
  exists; a 500 would be a lie about a tour that was created).
- Re-arm-path arm failure -> logged, **rethrown** -> Express 5 answers 500.
  This mirrors the patch write's own catch, which rethrows anything that is not
  a `ConditionalCheckFailedException`.
- Lost CAS -> logged, request **succeeds** (200). Spec 3.2: leave the winner's
  pointer.

### What S9 inherits

The re-arm branch's shape is now
`cancel -> arm (try/catch) -> CAS -> ladderChanged = true`. S9 replaces the
`cancelTourReminders` call with `deleteSupersededForTour` in place; the ordering
spec 3.2 wants (rotate -> sweep -> arm -> CAS) is already satisfied by
construction, because the rotation happens in the patch write ABOVE the branch.

2. **The prompt's suggested lever for the arm-failure test was wrong.** A
   throwing `settingsRepo` does NOT make `armTourReminders` throw:
   `readQuietHoursWindow` (`jobs/tourReminders.ts:314-329`) catches, warns and
   falls back to `DEFAULT_ORG_SETTINGS` by design. `HarnessOptions` has no
   settings override either. The working lever is
   `world.tourRemindersRepo.create` - the fake repos are exposed on `FakeWorld`
   and the app holds the same object references, so a post-build monkey-patch
   takes effect. Same lever drives the interleaving gate. S5/S8 will want this.
3. **`tours.get` after a lost CAS is a real extra read.** The worklist offers
   "splice or re-read" as equivalents; they are not. On a WIN a splice is exact
   (we know the value). On a LOSS the winner's value is unknown to this request,
   so only a re-read is honest - and it can come back `undefined` if the tour was
   deleted in between, which is why the assignment is guarded rather than `!`.
4. **`log.info({ tourId, fields: Object.keys(patch).length }, 'tour patched via
   api')` now counts the pointer** on rotating patches. Nothing asserts it (grep
   in section 4), but a human reading prod logs will see the field count tick up
   by one on reschedules and terminal transitions.

`rosterProvision.ts:398` was re-confirmed INERT by reading, not just by trusting
B#7b: it is `deps.tours.patch(tourId, { groupThreadId })` and `toursRepo.patch`
is a SET-merge, so `currentLadderId` survives it untouched. It never arms and
never sweeps.
