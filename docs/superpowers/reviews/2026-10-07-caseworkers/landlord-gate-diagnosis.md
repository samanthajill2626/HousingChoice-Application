## Change attribution and competing explanations

- **Direct e0da8da3 guard failure: unsupported for this action.** Between `b8dcd649` and `e0da8da3`, production changes are confined to generic contact PATCH handling. It captures the raw classification revision when type/role is patched, combines classification and note guards, and reports a guarded conflict (`app/src/routes/contacts.ts:1522`, `:1531`, `:1746`). No GET, navigation, rendering, inbound capture, or extraction behavior changed in that commit. The failed action had not reached the click that invokes this route. Even an ordinary triage rejection leaves the unknown pane and re-enables its buttons (`ContactDetail.tsx:672`), rather than intentionally replacing the document with white.
- **Broader feature regression: not ruled out by the narrow diff.** Relative to `d8749158`, `ContactDetail` imports caseworker UI, adds dialog state/actions, and supplies a caseworker action to `UnknownFile`; the landlord button text and triage action remain. The scenario file is unchanged, and the only feature edit in its shared steps changes unrelated property-send copy around `e2e/scenarios/steps.ts:1048`. Bootstrap, auth gate, single-contact hook, inbound capture, and extraction application files are unchanged across those revisions. Static inspection does not prove all new imports can never fail during development module loading.
- **Document/module/bootstrap failure: best-fit class, exact cause unknown.** An empty root before a successful React mount is consistent with the white screenshot and missing new auth traffic. A failed document response, module fetch/evaluation failure, browser problem, or unhandled root error remain candidate mechanisms. The Express log does not record Vite's complete document/module response history, and the screenshot cannot distinguish these. No particular mechanism is established.
- **Concurrent classification or stale contact state: weak fit to observed evidence.** A real classification writer could hide the triage pane on an otherwise-rendered contact, but the screenshot shows no rendered contact at all. Capture does not overwrite an existing kind. Extraction's type result creates a pending suggestion, not a direct classification (`app/src/services/extraction/apply.ts:576`), and its live reconciliation reads the type/revision (`:781`). The target extraction finishes after the final disconnect; its log alone cannot establish its payload. There is no observed browser refetch after that event. The standard configuration uses one test worker with no fully parallel tests (`e2e/playwright.config.ts:140`), while background jobs can still outlive earlier tests.
- **Phone/ID collision: possible in principle, not observed here.** The generator's timestamp suffix repeats every 100 seconds and sequence state is process-local; it is not a global uniqueness proof across worker restarts or separate processes. However, this test's exact phone resolved as unknown, a new contact was logged, both relay assertions passed, and the cached ID is reused. No evidence shows another actor classifying that ID. A collision does not by itself explain a white document.
