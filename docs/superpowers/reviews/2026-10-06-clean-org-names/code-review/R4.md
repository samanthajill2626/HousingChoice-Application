## R4-1 | LOW | CONFIRMED | app/src/services/orgRecords.ts:501 ; app/src/jobs/orgRewrite.ts:128, :149-150 ; app/src/services/orgRewrite.ts:272, :289-291 ; app/scripts/clean-org-names.ts:669, :678

**A pass paces its first beat from PASS START, so time spent before the pass is
invisible to it: the first records of a pass (up to 20 s of them) are written with no
lock check under a lock that already lapsed.** A11 moved the beat to the top of each
record, which catches a stall INSIDE a pass. But `rewrite()` starts its pacing clock
fresh (`let lastBeat = Date.now()`, orgRecords.ts:501) on every call, and the job calls it
once per field (jobs/orgRewrite.ts:150). Two stalls fall outside every pass:

(a) The claim's own write. The claim computes `heartbeatAt = at` in its change function,
BEFORE its Put is sent (orgRewrite.ts:272, :291). A Put that lands 16 minutes later (no
request timeout; two dead keep-alive sockets in a row - R3-BE-1's own trigger) stores a
heartbeat that is already stale on landing. Any list write in that window would fail the
Put on its version, so the add must come right after it lands:
1. 12:00 Clear "Metro HA" delivered on time; claim reads (fresh), `at` = 12:00, Put sent.
2. 12:16 the Put lands: `heartbeatAt` 12:00 - stale. The job gets `claimed`.
3. 12:16 add("Metro HA") passes refuseWhileRewritingName (stale) -> 201; a VA saves
   tenant t-new with it (D5: exact name).
4. Pass 1 starts, `lastBeat` = 12:16; tenants are the FIRST contact type visited, so
   t-new is reached inside the 20 s pacing window: no beat, REMOVE written.
5. The pass ends; finish() checks id and status only -> `done`.

(b) The tail of the previous pass. A rename/merge of a housing authority has two passes
(housingAuthority, then accepted_authorities). A stall in pass 1's LAST read (the final
`listByType('unknown', {deleted: true})` page, which visits no record) is followed by no
beat in pass 1; pass 2 resets its clock after the stall and writes unchecked for 20 s.
The harmful add needs the old name to be addable (a rename whose old-name spelling D12
skipped, e.g. `too_many`, or an admin removing it during the lapse), so (b) is narrower.

The cleanup has the same shape at its start: `lockedAt` is read before the acquire
(:577), but `lastBeat` starts after `peek()` (:669, :678), so a slow acquire or peek
leaves the first 20 s of rows unchecked. There it is benign (a concurrent rewrite's
records reappear in "Not on the list"), so the cleanup part is INFO.

Doc lines that now overclaim: jobs/orgRewrite.ts:17 ("so the pass STARTS under a fresh
lock") and :19 ("the first record after a stalled read is checked first");
services/orgRewrite.ts:289-290; orgRecords.ts:32-34. FW3-A's out-of-scope note 1 ("a
stalled read at pass start is still caught") is true only for a stall at the START of
the next pass.

Evidence (zz-review-R4-1.test.ts, fake world, real OrgNames/OrgRewrite/OrgRecords
services and runOrgRewriteJob, fake Date):
- (a) claim wrapped to land at 12:16 and let the VA act: logged
  `{"added":"added","outcome":{"outcome":"done","counts":{"housingAuthority":2,...}},"tNew":"(removed)","lock":{"status":"done",...}}`;
  `expect(tNew).toBe('Metro HA')` failed: expected undefined.
- (b) rename, fields [housingAuthority, accepted_authorities], pass 1's last read stalls
  12:00 -> 12:16 (the add and the property save at 12:15): logged
  `{"added":"added","outcome":{"outcome":"done",...,"accepted_authorities":1},"beats":0,"uNew":["Housing Authority of the City of Atlanta"]}`;
  `expect(uNew).toEqual(['Atlanta Housing Authority'])` failed.

Why LOW: the same 15-minute-stall trigger as R3-BE-1, with the VA's add and save also
inside the first seconds of a pass ((a)) or an unusual list state ((b)). When it happens,
the outcome is R1-ADV-BE-1's data loss on the records reached.

Fix (small, keeps every A6/A11 test's meaning; beat-count tests change):
1. Let `leasedHeartbeat` own the pacing - ONE clock across passes, started at
   `claimSentAt`: the pass calls it before every record and it calls through once 20 s
   have passed since the last SEND (claim or heartbeat). Minimal alternative: start each
   pass at `lastBeat = Number.NEGATIVE_INFINITY` (one extra list write per pass).
2. Judge an answer by its round trip: a claim or heartbeat that answers true at or after
   `sentAt + ORG_REWRITE_LEASE_MS` counts as lost (its stored heartbeat may be stale on
   landing). This also covers the one record written after a mid-pass heartbeat whose
   Put landed late.
3. Cleanup: start `lastBeat` at `lockedAt`.
Fix the four doc lines either way. Per the round-3 rule this is a LOW to file unless the
fix is taken.

## Charge 1c - A11 interleavings (job lease 14 min, cleanup lease 14 min)

1. Stall in a page read mid-pass: the next record's beat runs first (elapsed > 20 s) ->
   stale -> false -> lock_lost. Closed.
2. Every heartbeat throws: rethrown inside the lease, false past it. Job: records 2..35
   beat; the beat before record 35 at 12:14:10 stops it (34 writes at 25 s each, the
   last landing 12:14:10 < 12:15). Cleanup: beats at 5 and 10 min continue, 15 stops.
   Closed; the margin covers 20 s of pacing plus one write.
3. Heartbeat hangs then throws past the lease: judged at the throw -> stop. Closed.
4. Heartbeat hangs then answers true: `at` is computed after its read; any add meanwhile
   bumps the version, the Put fails, the re-read sees stale -> false. With no add, the Put
   can land already stale: the CURRENT record is written, then the next beat (paced from
   the send) fires at once and stops it - one unchecked record (R4-1 fix 2).
5. Claim lands late: R4-1(a). Open.
6. Stall at the tail of pass 1: R4-1(b). Open.
7. Two runs of one jobId (redelivery to a second worker): both refresh on success; one
   whose heartbeats fail past its lease stops without finish(), leaving the other's lock.
8. A heartbeat Put that landed but answered retryable (R3-BE-2 shape): the re-read finds
   its own fresh heartbeat -> true, writes again. Harmless.
9. finish() after the lease: the last pass can end inside the final pacing window, but the
   lock is still fresh then (it lapses at the stored heartbeat + 15 min >= lease start +
   15); a finish that itself hangs records done on a lapsed lock - no record harm
   (FW3-A out-of-scope 3).
10. Cleanup on a sleeping laptop: the next beat after wake fires at once (paced from the
    send) -> stale or past the lease -> CleanupLockLostError. Acquire/peek latency: R4-1.
