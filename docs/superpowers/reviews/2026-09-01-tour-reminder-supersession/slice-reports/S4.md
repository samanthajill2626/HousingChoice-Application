## 2. T4.1 write mechanism (the O6 choice)

**Mutate-then-re-Put**, not `UpdateCommand`. `seedLive` Puts its three tour rows
at `live.ts:459-468`, ~20 lines before the first arm, and `toursArr` holds those
exact object references - so setting `tour.currentLadderId` and re-Putting is
byte-identical to the first write plus one attribute, and it keeps this file's
single write mechanism (`PutCommand`) rather than introducing a second.

Shipped shape (`app/src/lib/seed/live.ts`, just below the `tourToday` /
`tourTomorrow` / `tourUpcoming` bindings):

```ts
const toursTable = namespace?.tableNameFor('tours') ?? tableName('tours');
const pointTourAtLadder = async (tour: TourItem, ladderId: string | null): Promise<void> => {
  if (ladderId === null) return;
  tour.currentLadderId = ladderId;
  await doc.send(new PutCommand({ TableName: toursTable, Item: tour }));
};
```

Called once after each of the three arms, BEFORE that arm's `console.log`. The
`ladderId === null` guard is the S2 contract's guard (S2 report section 5:
a tour with a `scheduledAt` never returns null today, but pointing at an EMPTY
generation would refuse any legacy row the tour still carries, so the guard is
written for meaning, not for a reachable path). All three live tours are
`status: 'scheduled'` - none is terminal - so none wants a rotated pointer.

No seed uses `randomUUID()`.

| seed | rows carry | tour pointer |
| --- | --- | --- |
| `live.ts` | the armer's minted `randomUUID()` (demo world is already not byte-stable) | the SAME id, re-Put onto the tour |
