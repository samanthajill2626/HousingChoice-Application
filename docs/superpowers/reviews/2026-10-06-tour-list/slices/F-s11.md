Why mutant 1 survived the plan's suite: the guard only matters in the window
React leaves between a default-lane COMMIT and its passive effects.
react-dom 19.2 schedules a commit's passive effects as a separate Scheduler
task (`react-dom-client.development.js:17919`); only a sync lane flushes them
at commit (`:18323`). An automatic answer that lands in that window is
written before the new run's cleanup aborts it, and the new run starts from
the cursor that answer is about to move past - so two writes from ONE cursor
reach the queue. Inside `act()` render, commit and the passive flush run in
one synchronous act-queue loop, so no act-driven test can open the window:
the mutant is equivalent under act. The new test runs OUTSIDE act on React's
real scheduler (`IS_REACT_ACT_ENVIRONMENT` false for its body, restored in
`finally`; `waitFor` to finish): the follow from f0 is held; a layout effect
of the very commit that turns the walk on lands it (cursor -> f1); the
walk's first run, started from the stale f0, is answered with a different
page ('stale'). With the guard that page is dropped and the walk continues
from f1. The test asserts the window was hit (`call(2)` is `{ cursor: 'f0',
limit: 100 }`). Coupling: it relies on react-dom deferring default-lane
passive effects; if a React upgrade flushes them at commit, this test fails
LOUDLY (rows `['stale']`) rather than passing vacuously - the guard would
then be unreachable and the test should be retired, not "fixed".

Why mutant 2 survived: a non-empty followed page already ends the follow
through `lastPageEmpty`, and Load more / Keep checking resets the count, so
none of the plan's paths lets a stale count act. Spec 4.5 says "up to 10 in a
row"; the count acts when a walk's empty page hands back to the follow: nine
empty follows and a full tenth, then a walk page empty with a cursor, then
the search cleared -> the follow must run (the mutant had counted 10 and
showed Keep checking instead).

## D-7 - how the walk cap is per walk

- `const [walkGen, setWalkGen] = useState({ walk, n: 0 })` and
  `if (walkGen.walk !== walk) setWalkGen({ walk, n: walk ? walkGen.n + 1 :
  walkGen.n })` - the listGen pattern (a CONDITIONAL setState in render on
  the walk edge); `walkSession = walkGen.n` bumps on every false -> true edge
  only.
- `ListState.walkFor` tags `walkRequests` / `walkCapped` with the session
  they count for (`freshState` sets 0 with zero counters - a zero count
  belongs to any session).
- Render derives `walkCapped = state.walkFor === walkSession &&
  state.walkCapped`; the automatic mode uses it, so another session's cap
  reads as not capped. The walk write counts `(s.walkFor === forWalk ?
  s.walkRequests : 0) + 1` and stamps `walkFor: forWalk` (`forWalk` captured
  by the effect; `walkSession` joins the effect's deps - it only changes on
  an edge that also changes `autoMode`).
- The returned `walkCapped` is that derived value: it stays true while the
  search is cleared (same session) and is false from the next walk on.
- eslint accepts both conditional setStates in render (exit 0, no warning).
