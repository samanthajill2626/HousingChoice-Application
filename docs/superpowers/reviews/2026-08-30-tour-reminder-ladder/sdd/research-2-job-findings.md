## GAPS

**G1 — The module header (`:1-32`) is stale today and gets worse.** Lines 6-8 read *"Rows whose clamped dueAt is already in the past (relative to `now`), lands at/after the tour start, or collides with a later rung's slot are **silently skipped**."* Two of those three write visible rows. Task 7 adds a fourth rule and a fifth reason token; the plan's Files list for Tasks 6 and 7 names only `:89-118` and `:248-314`, so the header is left describing behaviour that has not existed since 2026-08-04.

**G2 — `armTourReminders`'s own docblock (`:215-225`) enumerates the skip rules and is not in any task's edit list.** It says *"A rung whose clamped dueAt is already past is skipped with no row (pre-existing rule)"* — after Task 7 that is false for `day_before` and `morning_of`, the exact rungs the founder will be asking about.

**G3 — The pass-2 rule list at `:252-260` ((a)-(d)) is not in any task's edit list either.** Task 7's inserted comment sits *inside* the loop; the (a)-(d) enumeration above it will be missing rule (e) and will still open with the false "a skip creates NO row".

**G4 — Widening `ReminderSkipReason` silently widens `claimSkip`.** `claimSkip(reminderId, skippedAt, reason: ReminderSkipReason)` (`repos:136`) and `claimSkipRow(row, reason: ReminderSkipReason, ...)` (`jobs:508`) both accept the full union. Once `booked_too_late` is a member, `await claimSkipRow(row, 'booked_too_late', ...)` type-checks at all six claim-skip sites even though it is an ARM-ONLY reason. Nothing in the plan adds a guard or a narrowed arm-time subtype. Cheap mitigation: a dedicated `ArmTimeSkipReason` / `ClaimTimeSkipReason` split, or at minimum a comment at `claimSkipRow`.

**G5 — `ForceSendRefusal` deliberately does not include `ReminderSkipReason`, so `booked_too_late` will not appear there — correct, but the *converse* gap is live.** `forceSendReminder:1167` returns `{ outcome:'refused', reason:'tour_missing' }` when the **ROW** is not found (`rows.find(...) === undefined`), which the route surfaces to the operator as 409 `tour_missing` on a tour that demonstrably exists (the route already 404'd a missing tour at `:355`, and already 404'd a missing rung at `:360` — so `:1167` is in practice only reachable on a delete-between-checks race). Untouched by any task; it will read as a bug the moment an operator hits it.

**G6 — The Task 7 warn will fire on EVERY arm, including the seed and every unrelated PATCH.** `armTourReminders` runs at `routes/tours.ts:350` and `:1178` and at `lib/seed/live.ts:505/:516/:526`. Under `quietHoursStart <= 19:30` an org gets one WARN per booking, per reschedule, per status revival, and three per `seed:live` run. The plan's Step 3 snippet has no once-per-process or once-per-org dedupe and the plan does not discuss the volume. (Field names check out: `QuietHoursWindow` has `enabled`/`start`/`end`/`timezone` at `lib/quietHours.ts:11-16`, and `isQuietTime` gates on `enabled` at `:138` — the plan's "a disabled window never warns" claim is CORRECT.)

**G7 — Direct seed row writers are outside the plan's timing tasks.** `lib/seed/matrix.ts:973-1025` hand-writes reminder rows and derives `day_before` from `scheduledAt - 24h` (comments at `:878`, `:880`, `:985`). Those rows are PUTs, not arms, so Tasks 6/7 cannot break them — but after the retiming the matrix seed encodes a ladder production no longer produces, and `seedMatrixCoherence.test.ts`'s stated invariants (`:890-892`) will be describing a fiction. Task 10 says "seed writers that state the ladder … new timings + comments", which may or may not be read to include matrix's hand-written `dbf` variants. Make it explicit. `lib/seed/cast.ts:769-795` is the same shape (all `sentAt` history — harmless, but same staleness).

**G8 — `lib/performanceSeed.ts:167` wires a `tourReminders` repo that nothing writes.** `lib/seed/performance.ts` produces zero reminder rows. Not broken by this change; noted so a builder doing the Task 10 seed sweep does not chase it.

**G9 — No app-side test asserts the SKIP-REASON VOCABULARY is exhaustively handled.** There is no `satisfies Record<ReminderSkipReason, ...>` anywhere in `app/src`: `routes/tourReminders.ts:501` passes `skipReason` through verbatim, and `contactTimeline`/`relayGroups` filter skipped rows out entirely. So the ONLY thing that catches a half-added token is the dashboard's `REMINDER_SKIP_REASON_LABELS` Record type, which lives in a different workspace and a different typecheck project. The plan acknowledges this for `booked_too_late` specifically; the structural gap (nothing app-side enforces the vocabulary) persists and will bite the next token.

**G10 — Task 4 Step 6's replacement `composeBodyForRow` widens the `deps` Pick to `'unitsRepo' | 'contactsRepo'`, but `contactTimeline.ts:892-895` builds a `RunDueTourRemindersDeps` by CAST (`as unknown as RunDueTourRemindersDeps`) supplying only `conversationsRepo` and `unitsRepo`.** The comment at `:889-891` says exactly this: *"the compiler cannot tell us when RunDueTourRemindersDeps grows one."* That cast currently only feeds `resolveUsableGroup` (which touches neither), so it is safe today — but it is the one place in the tree where a `RunDueTourRemindersDeps` is fabricated without `contactsRepo`, and Task 4/5 push name resolution into deps. Any future reuse of that cast object for a compose path is a runtime `undefined.getById`. Worth a note in the handback even though this change does not trip it.

**G11 — Nothing in Task 6/7 addresses the `staleDayBefore` rule's interaction with the NEW `day_before` timing under the DEFAULT window.** `staleDayBefore` (`:294-295`) compares `localDateOf(clampedDueAt, tz) === tourLocalDate`. With the new 19:30-evening-before anchor and the default 21:00-08:00 window there is no clamp, so `localDateOf(dueAt) = tourLocalDate - 1` and the rule can never fire — which is the intent per spec 7.1. But the rule is then *dead code under the default configuration* and its only remaining coverage is Task 7's case 8 (`quietHoursStart: '19:00'`). If a builder deletes case 8 as "an unusual org config", the rule loses all coverage. The plan does not label case 8 as load-bearing for `staleDayBefore` itself; it labels it as the WARN test.

**G12 — Phase A leaves the fire-time quiet-hours backstop (`:729`) and the release-supersession backstop (`:707-721`) unreachable in production**, because the manual-only filter at `:470-471` empties `dueRows` first. Spec 7.3 states this for the backstop. Neither the spec nor the plan says what happens to their TEST coverage: `app/test/tourReminders.test.ts` reaches both only through the `NO_MANUAL_HOLD_BACK` wrapper (`:67-70`), i.e. the same divergence the dev tick has. That is fine, but it means the retiming's effect on those two backstops is proven ONLY under a configuration production does not run. Should be stated in the handback alongside the existing HARNESS TRAP paragraph.
