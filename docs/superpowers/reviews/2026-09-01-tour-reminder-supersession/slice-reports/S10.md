## The anchor derivation, byte-for-byte

`dashboard/src/routes/contact/streamAnchor.ts`:

```ts
const delta = sentinelBottom - viewportBottom;
if (delta > STREAM_ANCHOR_SLACK_PX) return null;
if (delta < 0 && hasBlock) return 'below';
return 'sentinel';
```

`STREAM_ANCHOR_SLACK_PX = 48`, exported so the test pins it rather than
re-spelling it. Bands, both `hasBlock` values, all unit-tested:

| delta | hasBlock true | hasBlock false |
| --- | --- | --- |
| `> 48` | `null` | `null` |
| `0 .. 48` | `'sentinel'` | `'sentinel'` |
| `< 0` | `'below'` | `'sentinel'` |

The `hasBlock:false` column is exactly `isAtBottom` (`scrollHeight - scrollTop -
clientHeight <= 48`), **including its negative half** - that closure returned
`true` for a fractional over-scroll, so the no-block column has to as well or
the regression net would drift. `below` is a DIRECTION test, which is what keeps
it reachable for a block shorter than 48px (unit-tested at delta -20, and again
in the e2e walk).

### DEVIATION 1 - the sentinel scroll is a rect DELTA, not `offsetTop`

The task and worklist both specify
`el.scrollTop = sentinel.offsetTop + sentinel.offsetHeight - el.clientHeight`.
**That formula is wrong in this DOM.** `.stream` is not positioned; the only
positioned ancestor is `.streamWrap` (`Timeline.module.css:74`), so the
sentinel's `offsetParent` is `.streamWrap` and its `offsetTop` includes
`.stream`'s own offset within that wrapper - i.e. the height of the
"Load older messages" row (`Timeline.tsx:2105-2119`), which appears and
disappears with `paging.hasOlder`. Every pin would be off by that height, on
exactly the threads that page.

Shipped instead:

```ts
el.scrollTop += sentinel.getBoundingClientRect().bottom - el.getBoundingClientRect().bottom;
```

Same two numbers the anchor is derived from, so the write and the derivation
cannot disagree; immune to `offsetParent`. Falls back to
`el.scrollTop = el.scrollHeight` when the ref is null. `scrollIntoView` is not
used and the code says why (it scrolls ancestors).

### DEVIATION 2 - no negative top margin (O9's "gap trim")

O9 says full-bleed + trim the doubled gap. Full-bleed is shipped
(`margin-inline: calc(-1 * var(--sp-3))`). The trim is NOT, and the measurement
is the reason:

- BEFORE: last message | `--sp-3` of `.stream`'s bottom padding | `.stream` box
  edge | dashed rule | `--sp-2` block padding | UPCOMING header.
- AFTER: last message | `--sp-2` of `.stream`'s gap | dashed rule | `--sp-2`
  block padding | UPCOMING header | ... | block end | `--sp-3` of `.stream`'s
  bottom padding | scroll end.

The gap does not double: `.stream`'s bottom padding MOVED BELOW the block, so
the 8px gap REPLACES the old 12px rather than adding to it. Space above the rule
went 12px -> 8px, i.e. tighter. Research G2 counted `gap + padding-top = 16px`
as one void, but the dashed border sits between them - it is 8 above and 8 below
a visible rule, which is the symmetric reading.

**Live QA (Phase 5) should check, at 360px and at desktop:**
1. the dashed rule and the `--c-surface-2` tint reach BOTH pane edges (the
   full-bleed) and no horizontal scrollbar appears in `.stream` - the block is
   sized to exactly the padding box, so a fractional rounding error would show
   as one;
2. the 8/8 spacing around the dashed rule reads right. If it reads cramped, the
   one-line fix is `margin-block-start: calc(-1 * var(--sp-2))` on `.upcoming`
   (rule flush to the last message) or `padding-top: 0` (header flush to the
   rule); both were considered and both are worse on paper.
3. the block no longer takes a fixed slice of a phone column - the composer must
   never be the thing that gives.

## What the worklist / research / the task got wrong

1. **`offsetTop` is the wrong measurement** (deviation 1 above). The worklist
   T10.5, the plan and this task all specify it verbatim. It is off by the
   "Load older messages" row's height whenever that control is rendered.
2. **"scrollTop unchanged within tolerance" contradicts spec 3.6.** The task's
   e2e assertion (3) asks for `scrollTop` to be unchanged when an inbound lands
   while the operator is on the block. Spec 3.6's `below` row says the opposite:
   preserve distance from the scroller's TRUE bottom - so `scrollTop` MUST move
   by the growth, precisely so the block does not slide down by the new
   message's height. The spec's rule is the correct one (holding `scrollTop`
   would push the block out of view, which is the yank acceptance 15 forbids), so
   the spec assertion is written as "the BLOCK's y is unchanged" plus
   "`scrollHeight - scrollTop` is unchanged". Both are stated in the spec's own
   comments.
3. **Research 6.2's "getBoundingClientRect is NOT mocked anywhere in
   Timeline.test.tsx" understates the consequence.** It is not just the
   stick-to-bottom block that needs a rect model - `describe('Timeline
   load-older control')` needs one too, and without it two of its cases went red
   (silently reading as at-bottom). Neither the worklist nor D 1.6 names that
   describe.
4. Research D 4.a's `> div > div` chains are SAFE: the section still contains a
   `<header>` and one `<div class=upcomingList>` whose children are the cards, so
   the four e2e sites (`steps.ts:3595`, `steps.ts:3677`,
   `placements-page.spec.ts:205`, `tour-comms-pane.spec.ts:226`) and the five
   dashboard ones resolve unchanged. `steps.ts` was NOT touched: no step helper
   needs the block.
5. Nothing surfaced that needed a STOP: exactly six scroll writers, exactly the
   five render sites research C 5 lists, no unexpected `upcoming` consumer.
