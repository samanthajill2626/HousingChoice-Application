# Reviewer B - independent design review

Scope: reviewed the design draft against the current repository and AWS CloudFront documentation. No code, Terraform, tests, stacks, or AWS resources were changed.

1. HIGH - The distribution-wide 503 mapping deliberately replaces current, actionable JSON error contracts, but the design gives no product decision or acceptance coverage for that regression. Evidence: the design makes API, auth, public, webhook, script, and media 503 responses HTML at `docs/superpowers/specs/2026-09-05-cloudfront-maintenance-page-design.md:76`; the running application uses 503 as a semantic response for an exhausted SSE connection cap at `app/src/routes/api.ts:2511-2518`, missing OAuth configuration at `app/src/routes/auth.ts:161-166`, and media/transcode availability at `app/src/routes/mmsMedia.ts:70-75` and `app/src/routes/mmsMedia.ts:125-129`. The dashboard currently exposes those codes to callers through `ApiError.code` at `dashboard/src/api/client.ts:68-75`. CloudFront documents that custom error responses are configured per distribution, while response-page lookup uses the matching cache behavior, so this cannot be limited to navigations by the proposed behavior (`https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HTTPStatusCodes.html`). Consequence: a healthy application can turn an actionable 503 such as `transcode_busy` or `oauth_not_configured` into generic maintenance HTML, breaking caller recovery and support diagnosis without an application outage. Correction: obtain and record a human decision that every app-origin 503 is intentionally replaced, enumerate the affected contracts and add an application-origin 503 regression fixture; otherwise select an architecture whose maintenance response is not a distribution-wide custom error response.

2. HIGH - The hosted activation requirement does not prove the load-bearing substitution path. Evidence: it only requires a direct maintenance-object 200 and unspecified "original-status fallback and recovery" at `docs/superpowers/specs/2026-09-05-cloudfront-maintenance-page-design.md:108`; the local browser test explicitly only fulfills a document and says it does not emulate the AWS edge at `docs/superpowers/specs/2026-09-05-cloudfront-maintenance-page-design.md:106-107`. AWS says CloudFront retrieves the response page through the behavior that matches its path after an origin error (`https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HTTPStatusCodes.html`). Consequence: a correct direct S3 page, Terraform apply, and observed 502/503/504 can all pass while an OAC/policy/path/origin association error makes CloudFront return its default error body instead. Correction: require an authorized dev-only fault exercise that requests a non-maintenance application URL, asserts the original selected status plus `text/html` and a unique rendered-page marker, then proves the same URL returns the recovered app response. Keep the direct page request as an additional origin-access check.

3. MEDIUM - The design incorrectly treats the deployment health gate as CloudFront traffic. Evidence: it says retaining 504 keeps the existing deploy `/health` check failing at `docs/superpowers/specs/2026-09-05-cloudfront-maintenance-page-design.md:74`, but the deploy script calls `http://localhost:8080/health` on the instance at `scripts/deploy.mjs:552-566`; the app deliberately exempts that local health route from the CloudFront origin-secret middleware at `app/src/app.ts:121-129`. Consequence: the rollout and surface inventory can mislead an operator into believing the feature validates or changes the deployment health gate, when no CloudFront error mapping is involved. Correction: state that the deploy health check remains an origin-local probe and is unaffected; separately define the CloudFront viewer-path recovery check in the hosted acceptance evidence.
